## 1. Context

The API already serves, without authentication, the league's teams (`GET /{slug}/equipos`) and the statistics of Spec 009 (standings per phase, top scorers, valla), which have been on in production since 2026-11-19. Spec 010 protects every route except `/health` with a per-client and per-class rate limiter. Nothing public yet lists a league's tournaments and phases, the matches of a phase, or what happened in a match; so a frontend cannot navigate. Spec 007 stores summaries of the current sheet, and Spec 008 defines publication as a pure function derived on each read (`SelectorDePublicacion`). Spec 008 C-07 left the read path to H19: with no publishable summary, a reader shows the structured facts of the sheet, never a draft. IA is off in every environment (`IA:Habilitada = false`), so production holds no summary today. There is no frontend project yet; ADR-09 fixes its hosting (an assets-only Cloudflare Worker).

## 2. Goal

A fan who opens the link of a league can browse its tournaments, the matches of each phase with their official state and score, the detail of a match with its facts and, when one is publishable, its summary, and the standings, top scorers and valla, from a frontend that keeps few calls per view and handles `429` without retry storms. Done when the tests of §6 pass and the production checks of §8.2 (which also verify the Spec 009 endpoints with positive controls, D2) are recorded.

## 3. Requirements (EARS)

### 3.1 League catalog (module `Torneos`)

| ID | Requirement |
| --- | --- |
| R-01 | The API shall expose, without authentication, `GET /{slug}/torneos`. The `200` body is `{"liga": {"slug", "nombre"}, "torneos": [{"codigo", "nombre", "fases": [{"orden", "tipo", "vueltas"}]}]}`. `liga` comes from the slug resolution that every public route already performs (Spec 002 R-27, ADR-14 §2.3): no other read of `ligas` is added. Tournaments are ordered by `codigo` (ordinal comparison); phases by `orden` ascending. A league with no tournament answers `200` with `"torneos": []`. |
| R-02 | If the slug does not exist, then the API shall answer `404`, with the same body as any public `404` (Spec 009 R-26). |

### 3.2 Matches of a phase (module `Torneos`)

| ID | Requirement |
| --- | --- |
| R-03 | The API shall expose, without authentication, `GET /{slug}/torneos/{codigo}/fases/{orden}/partidos`. If `codigo` breaks the code rule (Spec 005 R-12) or `orden` is not an integer ≥ 1, then `400`, before any database command. If the slug, tournament or phase does not exist in that league, then `404`. Error bodies follow Spec 005 R-24, as in Spec 009 R-26. |
| R-04 | The `200` body is `{"torneo": {"codigo", "nombre"}, "fase": {"orden"}, "partidos": [...]}`, with **every** match of the phase in any of the five states, each as `{"jornada", "programadoPara", "local": {"codigo", "nombre"}, "visitante": {"codigo", "nombre"}, "estado", "marcador", "oficial", "motivo"}`. Team codes and names are those of the league's teams (`equipos`). |
| R-05 | `estado` shall be the stored state of the match (`partidos.estado`, Spec 006 R-01), including the exception of Spec 006 C-32 (`Cancelado` over a withdrawn sheet). `marcador` {`local`, `visitante`}, `oficial` {`local`, `visitante`} and `motivo` shall come **only** from the current sheet (Spec 006 R-07); each is `null` when that sheet does not hold it, and all three are `null` at version 0. No value of any other version is read. |
| R-06 | Matches shall be ordered by `jornada` ascending, then `programadoPara` ascending with `null` last, then home team code, then away team code (ordinal comparisons). |
| R-07 | `programadoPara` shall be the scheduled time in UTC, written as RFC 3339 with the suffix `Z`, or `null` when the match has none. The API never converts it to a local time (presentation in `America/Bogota` is the frontend's job, R-45). |

### 3.3 Match detail: facts (module `IA`, reading `Torneos.Contracts`)

| ID | Requirement |
| --- | --- |
| R-08 | The API shall expose, without authentication, `GET /{slug}/torneos/{codigo}/fases/{orden}/partidos/{local}/{visitante}`. The match is identified only by this **natural key**: tournament code, phase order, home team code and away team code, the same key as the Admin sheet route (Spec 006 R-08). If a code breaks Spec 005 R-12 or `orden` is not an integer ≥ 1, then `400` before any database command. If the slug, tournament, phase or match does not exist in that league, then `404`. Codes are compared exactly (ordinal, case-sensitive), as stored. In a one-leg phase, the key with home and away swapped does not identify the match: it answers `404` (C-07). |
| R-09 | The `200` body is: `torneo` {`codigo`, `nombre`}, `fase` {`orden`}, `jornada`, `programadoPara` (R-07), `local` {`codigo`, `nombre`}, `visitante` {`codigo`, `nombre`}, `estado`, `marcador`, `oficial`, `motivo` (R-05), `goles` [{`equipo`, `jugador` {`codigo`, `nombre`}, `cantidad`}], `autogoles` [{`equipoDelAutor`, `equipoBeneficiado`, `jugador` {`codigo`, `nombre`}, `cantidad`}], `golesSinAutor` {`local`, `visitante`}, `tarjetasInformadas`, `tarjetas` [{`equipo`, `jugador` {`codigo`, `nombre`}, `color`, `cantidad`}] and `resumen` (R-14). `equipo`, `equipoDelAutor` and `equipoBeneficiado` are `"local"` or `"visitante"`; `color` is `Amarilla`, `Azul` or `Roja`. Player codes and names are the league's (`jugadores`), as in Spec 009 R-22. |
| R-10 | The facts of the body shall come from **one** object returned by the `Torneos.Contracts` read port (R-30): the current sheet of the match resolved to names (Spec 007 R-33). The same object shall build the canonical input of R-14. The team codes of `local` and `visitante` are the route values, which the port matched exactly. |
| R-11 | While the current sheet has no `marcador` (version 0, `Programado`, `Cancelado`, or `Adjudicado` without a sporting score), the body shall carry `goles` [], `autogoles` [], `golesSinAutor` `null`, `tarjetasInformadas` `null` and `tarjetas` []. While it has one, `golesSinAutor` and `tarjetasInformadas` are those of the sheet, and `tarjetas` is non-empty only when `tarjetasInformadas` is `true` (Spec 006 R-11 e, j). |
| R-12 | `goles` and `tarjetas` shall be ordered by side (`local` first), then player name, then player code, then (`tarjetas` only) color, all ordinal; `autogoles` by `equipoDelAutor`, then name, then code. |
| R-13 | The body shall never contain the sheet version, the rectification reason, the Admin's `sub`, any save time, any internal identifier (`Guid`), registration identifiers or any member not listed in R-09 (I-01). |

### 3.4 Match detail: published summary

| ID | Requirement |
| --- | --- |
| R-14 | The detail use case shall build `EntradaCanonica.Construir(datos)` from the object of R-10 and call `SelectorDePublicacion.Seleccionar(resumenes, entrada)` (Spec 008 R-17) with **every** stored summary of that match (R-15). When the selector returns a row, `resumen` shall be `{"texto": <its text>, "origen": "Modelo" \| "Plantilla"}` (C-09); otherwise `resumen` shall be `null`. |
| R-15 | `IAlmacenDeResumenes` (Spec 007) shall gain a read of **all** summary rows of one match of the current tenant, inside the caller's transaction (it throws `TransaccionRequeridaException` without one, as its other members do), with no filter by state, fingerprint or text. The number of rows is bounded by the number of distinct fingerprints of that match (one row per (match, fingerprint), Spec 007 R-01). |
| R-16 | No code of the detail path other than `SelectorDePublicacion` shall decide publication: the detail use case and its endpoint shall not reference `EstadoDeResumen`, `VisibilidadDeResumen`, `VerificadorDeResumen`, nor the members `Estado`, `Huella` or `MotivoBorrador` of `ResumenPartido`, and the use case shall reference `SelectorDePublicacion.Seleccionar` (anti-empty). |
| R-17 | If no summary is publishable, then the body shall not reveal why. For the same facts, the bodies shall be byte-identical when the match has no summary row, only a `Borrador`, only rows of a stale fingerprint, or a `PorVerificar` row whose text the current verifier rejects. No body reveals the existence, number, state, draft reason, model, prompt version, fingerprint or call of any summary row. |
| R-18 | The detail shall not depend on `IA:Habilitada`: with IA off, the route is mapped, its dependencies resolve at startup (`ValidateOnBuild`), and it publishes a stored row exactly as R-14 says. It shall never call the provider, reserve budget, write a row or publish an event (C-10). |
| R-19 | The three read use cases of this Spec shall write nothing: no insert, update, outbox row or budget change. |

### 3.5 Consistency, isolation and cost

| ID | Requirement |
| --- | --- |
| R-20 | Each request to a route of R-01, R-03 or R-08 shall run in **one** transaction opened with `IUnidadDeTrabajo.IniciarLecturaConsistenteAsync` (`REPEATABLE READ`, Spec 009 R-33), with the tenant set as in every transaction (ADR-14 §2.3). In the detail, the facts, the canonical input and the summary rows come from that one snapshot (owner, R4). The same holds for the catalog and the phase list (C-12). The transaction holds no wait other than its own database commands: no external I/O inside it. |
| R-21 | The number of database **commands** of each route shall not depend on the number of tournaments or phases (R-01), of matches (R-03), or of goal rows, card rows and summary rows (R-08). This bounds round trips only (no N+1); the rows read, the memory and the work in process grow with the data and are bounded by the limits of §4 (Cost), not by this requirement. In the detail, the selector scans the summary rows of the match once and runs the verifier at most once (only on the candidate with the current fingerprint, Spec 008 R-17). |
| R-22 | Responses shall be deterministic: the same stored data gives byte-identical bodies whatever the insertion order of the rows. Every order is defined by this Spec, with ordinal comparisons; nothing depends on the clock or the culture. |

### 3.6 Security, rate limit and observability

| ID | Requirement |
| --- | --- |
| R-23 | The three routes shall use no authentication and no identity: a request with an `Authorization` header gets the same response as one without it, and nothing reads the header. |
| R-24 | The three routes shall be of class `publica` (Spec 010 R-09) under the single global limiter (Spec 010 R-10), with no endpoint policy and no exclusion; a rejected request gets the `429` of Spec 010 R-13 and runs no endpoint code (Spec 010 R-15). |
| R-25 | Isolation between leagues rests only on the EF Core filter `Tenant` and RLS (ADR-14); no route uses `IgnoreQueryFilters` or raw SQL. A summary stored for another league is never published, **even when its fingerprint equals the fingerprint of this match** (identical names and results in two leagues give identical canonical inputs; C-14). |
| R-26 | The use cases shall log through `ILogger<T>`: tenant, route, tournament code, phase order, row counts and, in the detail, whether a summary was published (boolean). Never a team or player name, a summary text, a fingerprint, the client IP or a `sub` (CLAUDE.md, Spec 007, Spec 010 R-16). |
| R-27 | The three routes shall be mapped in every environment, with no setting (C-11). |

### 3.8 Frontend (project `web/`)

| ID | Requirement |
| --- | --- |
| R-33 | The frontend shall be a single-page application in `web/` with Vue (Composition API), TypeScript, Vite, Pinia and Vitest (`CLAUDE.md`), plus `vue-router` (C-17; `CLAUDE.md` amended in PR 2, K-3). Runtime dependencies are exactly `vue`, `vue-router` and `pinia`; HTTP uses the native `fetch`. Versions are verified against official sources in the handoff. |
| R-34 | The routes shall mirror the API paths: `/:slug` (league), `/:slug/torneos/:codigo/fases/:orden/partidos` (matches tab, the tournament's default view), `/:slug/torneos/:codigo/fases/:orden/posiciones`, `/:slug/torneos/:codigo/goleadores`, `/:slug/torneos/:codigo/valla`, and `/:slug/torneos/:codigo/fases/:orden/partidos/:local/:visitante` (detail). Each tab is a route, so each table loads only when its route is opened (owner, R5). `/:slug/torneos/:codigo` redirects to the matches of its phase with the lowest `orden`. Any other path shows the "not found" view. |
| R-35 | The root `/` shall show no league catalog (owner, R1): only a fixed text saying that each league shares its own link. |
| R-36 | Every API request shall be a `GET` to `VITE_API_BASE_URL` + a path whose every route value is encoded with `encodeURIComponent`, with `credentials: "omit"` and no header other than `Accept: application/json`, so that the browser sends no preflight (C-18). Links to a match detail are built only from the codes of a list body, never from user input. |
| R-37 | The frontend shall make exactly these API calls **per navigation**, counting only requests that reach the network and depending on what the store already holds: **(a)** opening `/:slug` → 1 (`torneos`) if the league's tournaments are not in the store, else 0; **(b)** opening a tournament tab (`partidos`, `posiciones`, `goleadores` or `valla`) → 1 for that tab's resource if it is not in the store, else 0, **plus** 1 (`torneos`) only if the league's tournaments are not in the store; **(c)** opening a detail → 1 if it is not in the store, else 0; **(d)** "Actualizar" → 1, for the current view's resource only. So entering a tournament **from a loaded league page** costs 1 call, and reaching it **from an empty store** costs 2 in total: 1 + 1 when the fan opens the league link and then the tournament, or 2 in one navigation for a deep link (owner, R5; C-05). No other request is made: no polling, no prefetch, no automatic refresh. |
| R-38 | The Pinia store shall keep each loaded response for the life of the page, keyed by its API path; "Actualizar" replaces only the current view's entry; a page reload empties the store. Each view shows the time it was loaded, in `America/Bogota` (C-16). Nothing is persisted: no polling and no cache beyond the page's memory. A failed, aborted or timed-out response is never stored. |
| R-39 | If the API answers `429`, then the frontend shall not retry automatically (owner, R5): it shows a message that the service is busy and a manual "Reintentar" button. When `Retry-After` is an integer number of seconds, the button stays disabled with a countdown until it reaches zero; when it is absent or not an integer, the button is enabled at once and no countdown is shown. |
| R-40 | If the API answers `404`, then the view shows "not found"; if the standings or the valla answer `409` with `configuracion_pendiente` (Spec 009 R-25), then the view says that the table waits for the league's configuration, with no partial table; on any other error or a network failure, a generic message and a manual "Reintentar". No error causes an automatic retry. |
| R-41 | While a request is pending, the view shows a loading state; after 10 seconds it adds an informative message that the server may be starting. If the response has not arrived after **30 seconds**, then the frontend shall abort the request with an `AbortController` and show a controlled timeout error with a manual "Reintentar"; it never retries by itself (C-19). The 30-second limit covers the whole request, from sending to the end of the body. |
| R-42 | The displayed result shall follow the state (C-22): `Jugado` → `marcador`; `Adjudicado` → `oficial`, labeled as an official result with its `motivo` (`WalkOver` as "W.O.", `Sancion`, `Otro`); `Suspendido` → partial `marcador`, labeled suspended with its `motivo`; `Programado` → the scheduled date and time, or "Por programar"; `Cancelado` → "Cancelado". The frontend computes no score: it only chooses which field to show. |
| R-43 | The standings, top scorers and valla views shall show the bodies of Spec 009 R-27 as returned: the `Provisional` state of the rules as a visible mark, the unresolved ties of `empates`, and the coverage numbers (`cobertura`). The frontend recalculates and reorders nothing. |
| R-44 | The detail view shall show the facts of R-09; cards only when `tarjetasInformadas` is `true` ("Sin tarjetas" when the list is empty), "Tarjetas no informadas" when it is `false`, and nothing about cards when it is `null`. When `resumen` is not `null`, it shows its text, marked by `origen` (C-09); when it is `null`, it shows no summary section and no message about summaries (Spec 008 C-07). |
| R-45 | Dates and times shall be shown in `America/Bogota` with `Intl.DateTimeFormat` and an explicit `timeZone`, independently of the device's zone (`CLAUDE.md`). |
| R-46 | Team names, player names and summary texts are untrusted data (Spec 007): they shall be rendered only by text interpolation. `v-html`, `innerHTML` and equivalent sinks are forbidden in the project (lint error). |
| R-47 | The bundle shall embed no secret and no environment value other than `VITE_API_BASE_URL` (ADR-09 R-05). If a production build runs with `VITE_API_BASE_URL` missing or not starting with `https://`, then it shall fail. The frontend uses no cookies and no browser storage. |
| R-48 | The interface shall be in Spanish (Colombia). |

### 3.10 Invariants

| ID | Invariant |
| --- | --- |
| I-01 | No body of R-01, R-03 or R-08 contains a `Guid`, a `sub`, a sheet version, a rectification reason, a fingerprint, a summary state, a draft reason, a model, a prompt version or a call identifier. |

## 4. Non-functional constraints and preconditions

- **Personal data:** players appear with code and name only, as in Spec 009 (Estado §2). Cards per match and per player become public (owner, R3 sub-decision); a public fair-play table or suspensions stay out of scope (§7).
- **Cost:** two different bounds. **Commands** (round trips) are constant per route (R-21, T-08). **Rows, memory and in-process work** grow with the data and are bounded by the existing limits: a phase list reads at most the matches of a tournament (Spec 005 R-16: 1,000), and the catalog at most its tournaments and phases (8 phases per tournament); a detail reads one match, its current sheet rows (bounded by Spec 006 R-12: scores 0 to 99, card quantities 1 to 9) and its summary rows (one per distinct fingerprint, Spec 007 R-01), and runs the verifier at most once. No response time, memory or CPU bound is asserted in CI; production latency, including the cost of `REPEATABLE READ`, is measured and reported, not gated (§8.2 step 4).
- **Calls per view and shared addresses:** with `publica` at 120 per client and 600 global per minute (Spec 010 C-10), R-37 is what keeps a CGNAT address usable.
- **Preconditions:** Spec 010 implemented and verified in production (done, 2026-11-19); `Estadisticas:EndpointsPublicosHabilitados` on in Render (done, 2026-11-19); for PR 2, the Cloudflare secrets and the repository variable exist (D4), and the CORS origin of R-52 is saved in Render with "Save only" before the PR 2 merge (C-20); no migration is pending.

## 10. Risks and open items

- **IA off:** production publishes no summary; the positive publication path is proven only in CI (T-04 to T-07, T-09) until the owner turns IA on (§8.2, limits).
- **Stale screens:** with C-16, a view can be old until "Actualizar" or a reload; the load time is shown.
- **Cold start and timeout:** the first request after idle can take seconds; it is not measured with EF Core yet (Estado §9). Past 30 seconds the fan sees the timeout error and retries by hand (C-19); an aborted request may already have counted against the rate limit.
- **Isolation cost:** `REPEATABLE READ` on every public read (C-12) has a cost that is observed in production (§8.2 step 4), not assumed.
- **Coupling:** the public facts reuse `DatosDePartidoParaResumen`, the input contract of A-01. A future change to that contract changes the public body; T-03 will detect it.
- **Code renames:** links break if a league changes a team or tournament code (C-07).
- **Shared addresses:** R-37 keeps a cold tournament view at 2 calls cumulative and a tournament entered from a loaded league at 1; heavy tab use behind one CGNAT address can still reach `429` (Spec 010 C-10).

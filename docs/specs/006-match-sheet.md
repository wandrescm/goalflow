## 1. Context

Spec 005 loads tournaments and scheduled matches; a match is only `Programado` or `Cancelado`. The pilot needs the Admin to record, after each match, the sporting score, who scored (including own goals and goals nobody recorded), cards, and whether the match finished, was suspended or was decided administratively. Results are corrected often in amateur leagues, so every correction must keep the previous record, say why when it changes the nature of the result, never count a goal twice and never lose a concurrent change, whether that change comes from another correction or from an import. Each effective save is the producer ADR-02 was built for: `PartidoGuardado` with the match version.

Today the import resets any non-cancelled match to `Programado` (`ImportacionDeTorneo`, `partido.Reactivar()`), so re-sending an unchanged fixture after a result exists would silently erase its state. This Spec closes that.

## 2. Goal

An Admin can read and save the complete score sheet of a match of their league; an identical save writes nothing; a stale or concurrent change (another correction or an import) gets `409` and loses nothing; every effective save is a new immutable version published as `PartidoGuardado` in the same transaction; and an import can change neither the result, the sheet versions nor the protected attributes of a match with a result, only the schedule changes this Spec allows.

## 3. Requirements (EARS)

### 3.1 States and stored model

| ID | Requirement |
| --- | --- |
| R-01 | A match shall be in one of five states: `Programado`, `Jugado`, `Suspendido`, `Adjudicado`, `Cancelado` (check constraint). `partidos` shall gain `version` (integer ≥ 0, initially 0): the number of the current sheet version; 0 means no sheet was ever saved. |
| R-02 | Each effective save shall create one row in `planillas` for (tenant, match, version ≥ 1) holding: the state it sets; the sporting score (home and away, both present or both absent); the official score (both present or both absent); the sporting reason (absent or one of R-11); the rectification reason (absent or one of R-14); `tarjetas_informadas` (true, false or absent, R-11 j); the authenticated Admin's `sub`; and the save time from the database clock. (tenant, match, version) shall be unique. |
| R-03 | `goles` shall store, per sheet, rows of (type, credited participation, registration, quantity): type `Jugador`, `Autogol` or `SinAutor`; registration absent if and only if the type is `SinAutor` (check constraint); quantity ≥ 1. At most one row per (sheet, type, credited participation, registration), treating an absent registration as a value (`NULLS NOT DISTINCT`), so unattributed goals are one row per sheet and credited team. |
| R-04 | `tarjetas` shall store, per sheet, rows of (registration, color, quantity): color `Amarilla`, `Azul` or `Roja`; quantity 1 to 9 (check constraints). (sheet, registration, color) shall be unique. |
| R-05 | Every new foreign key shall be composite with `tenant_id` and `torneo_id` (ADR-14 §2.11): sheet → match; goal → sheet; goal → credited participation; goal → registration; card → sheet; card → registration. The referenced keys shall be alternate keys (`tenant_id`, `torneo_id`, `id`), added where missing (`partidos`, `planillas`, `inscripciones_jugador`). All use `ON DELETE RESTRICT`. Every unique constraint includes `tenant_id`. Primary keys are generated by the server (`Guid.CreateVersion7()`). |
| R-06 | `planillas`, `goles` and `tarjetas` shall carry `TenantId`, the EF Core filter `Tenant` and RLS with the tenant policy, in the same migration. `goalflow_app` shall have `SELECT` and `INSERT` on them, and **no** `UPDATE` or `DELETE`. `partidos` keeps `UPDATE` (state, version and schedule) and no `DELETE`. |
| R-07 | The **current sheet** of a match is the `planillas` row whose version equals `partidos.version`. `partidos.estado` shall always equal the state of the current sheet; with version 0 it is `Programado` or `Cancelado`. The only exception is a match cancelled by the import after its sheet was withdrawn (C-12): it is `Cancelado` while its current sheet is `Programado` (C-32). Sheet saves write both in the same transaction. |

### 3.2 Contract and validation

| ID | Requirement |
| --- | --- |
| R-08 | The API shall expose `GET` and `PUT /{slug}/admin/torneos/{codigo}/fases/{orden}/partidos/{local}/{visitante}/planilla` behind the Admin filter of ADR-01 (404 → 401 → 403). `codigo`, `local` and `visitante` follow the code rule of Spec 005 R-12; `orden` is an integer ≥ 1. If a route value is malformed, then `400`. If the tournament, phase or match does not exist in the caller's league, then `404`, decided after the Admin check. |
| R-09 | The `PUT` body is the **complete** desired sheet: `versionEsperada` (integer ≥ 0, required), `estado` (`Programado`, `Jugado`, `Suspendido` or `Adjudicado`, required), `marcador` {`local`, `visitante`}, `oficial` {`local`, `visitante`}, `motivo`, `motivoRectificacion`, `tarjetasInformadas` (boolean), `goles` [{`jugador`, `cantidad`}], `autogoles` [{`jugador`, `cantidad`}], `golesSinAutor` {`local`, `visitante`}, `tarjetas` [{`jugador`, `color`, `cantidad`}]. Missing lists mean empty; missing `golesSinAutor` means 0 and 0. Players are referenced by their league code; the server resolves the registration in this tournament, and from it the player's team. No team field is sent for a player. |
| R-10 | If the body is not valid JSON or contains a member the contract does not define (including `version`), then `400`; if it exceeds 64 KiB (declared or read), then `413` (bounded reader of Spec 005 C-23). Nothing is written. |
| R-11 | The sheet shall satisfy the rules of its state, independently of the stored state: **(a)** `Jugado`: `marcador` required; `oficial` and `motivo` absent. **(b)** `Suspendido`: `marcador` (partial) required; `motivo` one of `Clima`, `Luz`, `Disturbios`, `Otro`; `oficial` absent. **(c)** `Adjudicado`: `oficial` required; `motivo` one of `WalkOver`, `Sancion`, `Otro`; `marcador` optional. **(d)** `Programado` (sheet withdrawn): no `marcador`, `oficial`, `motivo`, `tarjetasInformadas`, goals or cards. **(e)** Goals and cards only when `marcador` is present. **(j)** `tarjetasInformadas` is required when `marcador` is present and absent otherwise; `tarjetas` may be non-empty only when it is `true`. `true` with an empty list means "zero cards confirmed"; `false` means "disciplinary information not received". |
| R-12 | The sheet shall satisfy, as a whole: **(f)** every player code resolves to a registration of this tournament whose participation is the home or the away team of this match; **(g)** for each side: goals of type `Jugador` by that side's players, plus own goals by the **other** side's players, plus `golesSinAutor` of that side, equal that side's `marcador`; **(h)** a player code appears at most once in `goles`, at most once in `autogoles`, and at most once per color in `tarjetas`; **(i)** scores 0 to 99, goal quantities ≥ 1, card quantities 1 to 9, `golesSinAutor` ≥ 0. |
| R-13 | If the sheet fails R-11 or R-12, then the API shall answer `422` with **every** error, each with its path in the request and an error code, and write nothing. Error bodies follow Spec 005 R-24 (natural keys of the caller's league only; no internal ids, constraint names or SQLSTATE). |
| R-14 | **Rectification rule**, evaluated against the current state *s* and the requested state *t* only after R-16 and R-18 (so it never turns an identical retry or a stale request into a `422`): **ordinary** (`motivoRectificacion` must be absent): `Programado` → `Jugado`, `Suspendido` or `Adjudicado` (first record); `Suspendido` → `Jugado` or `Adjudicado` (completion or resolution); *t* = *s* with different content (correction in the same state). **Exceptional** (`motivoRectificacion` required, one of `ErrorDeRegistro`, `PartidoEquivocado`, `DecisionReglamentaria`, `Otro`): `Jugado` → `Suspendido` or `Adjudicado`; `Adjudicado` → `Jugado` or `Suspendido`; `Jugado`, `Suspendido` or `Adjudicado` → `Programado` (sheet withdrawal). `Programado` → `Programado` with a different content is invalid. A request that differs from the current sheet **only** in `motivoRectificacion` (added, removed or changed) is invalid: a reason is never edited on its own. A violation is `422` with code `rectificacion_invalida` and writes nothing. |
| R-15 | If the match is `Cancelado`, then `PUT` shall answer `409` and write nothing; `GET` answers `200` with that state. |
| R-16 | `GET` shall answer `200` with `version` and the current sheet, including `motivoRectificacion` and `tarjetasInformadas` when stored. The sheet members of `GET` are exactly the `PUT` members except `versionEsperada`; `GET` adds `version`. A client builds a `PUT` from a `GET` body by removing `version` and sending its value as `versionEsperada`; the rest is sent unchanged. With version 0, `GET` returns `version` 0, the state and an empty sheet. `motivoRectificacion` describes the change that produced the version where it is stored; it is **never carried over**. Sending it back unchanged with an unchanged sheet is an identical save (R-17); a later ordinary change must omit it (R-14) and is stored without a reason, while the earlier version keeps its own; a later exceptional change carries its own reason. |

### 3.3 Saving, versions and concurrency

| ID | Requirement |
| --- | --- |
| R-17 | When the normalized desired sheet equals the current sheet (state, both scores, both reasons, `tarjetasInformadas`, and the sets of goal and card rows after resolution), the API shall answer `200` with `resultado: "sinCambios"` and the current version, and write **no row**, whatever `versionEsperada` says. Order of evaluation: `400`/`413` → `404` → R-11 and R-12 (`422`) → R-15 (`409`) → R-17 (`200 sinCambios`) → R-18 (`409`) → R-14 (`422`) → R-19 (save). |
| R-18 | If the sheet differs and `versionEsperada` is not the current version, then the API shall answer `409` with the current version and write nothing. |
| R-19 | When the sheet differs, `versionEsperada` equals the current version *n* and R-14 holds, the system shall, in **one** unit-of-work transaction: insert sheet version *n* + 1 with its goal and card rows, set `partidos.version` to *n* + 1 and `partidos.estado` to the sheet's state, and publish `PartidoGuardado` (R-24). The API answers `200` with `resultado: "guardada"` and version *n* + 1. |
| R-20 | `partidos` shall carry a **row-version concurrency token** that changes on every update of the row, whoever makes it (a `uint` shadow property configured with `IsRowVersion()`, mapped by Npgsql to the system column `xmin`; no column is added). Every update of a match, by the sheet **or by the import**, is conditioned on the token read in the same unit of work. If another transaction changed the match after it was read (another sheet save, or an import that cancelled, reactivated or rescheduled it), then the operation shall answer `409` and write nothing (never `500`); its sheet version, goal and card rows and event are not persisted. This holds also when both sheet requests carried the same content (C-07). The unique (tenant, match, version) of `planillas` is a second guard. Depending on the order in which the statements run, the loser of a race between two saves can fail through any of three errors, and the sheet store adapter shall translate **exactly** these three into one version-conflict exception, answered as `409` with code `conflicto_de_version`: the concurrency failure of the row-version token; a `23505` on the unique version index of `planillas`; and the duplicate-delivery exception of `Mensajeria`, **only** when every delivery row pending in the failed save is of `torneos.partido-guardado` for this tenant, this match and version *n* + 1 (C-30). To make that check possible, the duplicate-delivery exception shall expose the logical keys (tenant, event, aggregate, version, consumer) of the delivery rows pending in the failed save, taken from the change tracker by the `SaveChanges` override that already raises it (an additive change to Spec 004; its tests stay unchanged). A duplicate-delivery exception for any other key keeps its own behavior. Every other database error passes through unchanged. The `409` body carries no constraint name, SQLSTATE or internal identifier. The transaction is disposed without commit, so none of the loser's sheet, goal, card or delivery rows persist. No lock statement and no raw SQL is used. **Scope of the token (C-29):** it detects changes made by another transaction between the read and the write **of the same server operation**. It is not exchanged with the client, so it does not detect every change since the Admin opened the form: the sheet's staleness is detected by `versionEsperada` (R-18), a cancellation by R-15 (state read in the operation), and a reschedule, which does not move the sheet version, is accepted silently. |
| R-21 | Sheet versions shall never be modified or deleted; a correction, a rectification or a withdrawal of the sheet is a new version. |
| R-22 | The save use case shall log through `ILogger<T>`: tenant, tournament code, phase order, version, states and outcome; never a player or team name. |

### 3.4 `PartidoGuardado`

| ID | Requirement |
| --- | --- |
| R-23 | `PartidoGuardado` shall live in the `Contracts` sub-namespace of the `Torneos` module (Spec 004 R-02), with the constant name `torneos.partido-guardado`, and carry only `TenantId`, `AgregadoId` (the match id) and `Version`. |
| R-24 | It is published through `IPublicadorDeEventos` only by R-19, once per new version, inside the save transaction. Identical saves, rejected saves and imports publish nothing. If the save fails after publishing (concurrency conflict or any other error), then no delivery row shall persist. |
| R-25 | The production event-contract rule (Spec 004 T-25) shall evaluate **exactly** {`PartidoGuardado`} (anti-empty: today it evaluates no production event). |

### 3.5 Import (amends Spec 005)

| ID | Requirement |
| --- | --- |
| R-26 | In the import, `cancelado: false` shall match any stored state other than `Cancelado`: no write, counted unchanged. Only a `Cancelado` match returns to `Programado` (Spec 005 R-40). |
| R-27 | If the import marks as cancelled a match in `Jugado`, `Suspendido` or `Adjudicado`, then `409` (conflict type `partido_con_resultado`, key phase/home/away), nothing written. |
| R-28 | If the import changes the matchday of a match that is not `Programado` or `Cancelado`, or the scheduled time of a match in `Jugado` or `Adjudicado`, then `409` (same conflict type). The scheduled time of a `Suspendido` match may change (counted as updated); its matchday, state, version and sheets do not (C-09). |
| R-29 | If the import marks as withdrawn a team that has a match in `Jugado`, `Suspendido` or `Adjudicado`, then `409` (conflict type `retiro_con_resultados`, key team code), nothing written. Withdrawal after results needs a regulation decision (out of scope). |
| R-30 | The import shall never change `partidos.version` or write to `planillas`, `goles` or `tarjetas`. If a match it updates was changed by another transaction after it was read (R-20), then the import shall answer `409` (the existing concurrent-conflict answer of Spec 005 R-23) and write nothing: the import store adapter translates the concurrency failure of the token into the existing `ConflictoConcurrenteException`, in addition to the unique violations it already translates. |

## 4. Non-functional constraints

- **Isolation tests** against PostgreSQL 17 as `goalflow_app`; invented data only (`liga-a`, `liga-b`, `EQ-01`, `J-07`, `Jugador Uno`).
- **One transaction per save**; the save reads the match, its current sheet and the registrations of its two teams, and nothing else.
- **Deterministic concurrency tests (C-24).** The save and the import read and write through Application ports (the existing `IAlmacenDeImportacion` and a new sheet store port). Concurrency tests replace the real adapter, in the **test host only**, with a decorator that delegates to it and waits on a gate after the read returns. A test proves the interleaving it claims by asserting the gate events it observed (for example, "both reads returned before either write started"). No test-only code is registered in production. A barrier around two HTTP requests alone is not accepted as proof.
- **No personal data** beyond what Spec 005 stores; the Admin's `sub` is an internal identifier, never returned by any response of this Spec.
- **No new packages.**
- **Times:** the save time comes from the database clock (column default), in UTC.

## 5. Clarifications

| # | Question | Decision | Decided by / date |
| --- | --- | --- | --- |
| C-01 | Must player goals add up to the score? | Not to the official one. Sporting goals (player, own goals, unattributed) add up to the **sporting** score (R-12 g); the official score is the sporting one (`Jugado`) or the adjudicated one (`Adjudicado`). The naive rule fails in 4 of 4 cases (own goal, unattributed, walkover, suspended then adjudicated). | Owner, 2026-11-08 (predicted 4 of 4) |
| C-02 | Own goals? | The row references the **scorer's** registration and is credited to the opponent; it never counts for the scorer as a goal. Not configurable. The credited team is derived from the scorer's team, never sent (R-09), so it cannot be inconsistent. | Owner (P-02) and mentor, 2026-11-08 |
| C-03 | Unattributed goals? | Allowed, per side (`golesSinAutor`), stored as one row per sheet and credited team with no registration (R-03). The sum check of R-12 (g) makes the Admin account for every goal: a forgotten scorer is a `422`, not a silent unattributed goal. | Owner, 2026-11-08 |
| C-04 | How is a sheet corrected without `DELETE`? | Option B: immutable versions; the current one is `partidos.version`. The database enforces immutability: no `UPDATE` or `DELETE` on the sheet tables (R-06). Rejected: `DELETE` on `goles` (loses evidence) and `jsonb` (no composite keys to registrations). | Owner, 2026-11-08 |
| C-05 | One row per goal, or one row per (type, credited team, player) with a quantity? | Aggregated (R-03). One row per goal could be compared as a multiset; the aggregated model is chosen because, for sheets without minutes or individual events, it simplifies the contract, gives each row a natural identity and makes equality a set comparison. Owner's prediction for the 3–1 sheet corrected once (J-30's goal becomes unattributed): **6 rows** (3 + 3) — correct. | Mentor (proposed) and owner (approved), 2026-11-08 |
| C-06 | Does an identical save create a version or an event? | No (R-17). Content is compared **before** the version, so a retry after a lost response (`versionEsperada` = 3 while the current version is 4 with the same content) is `200` with no write. | C-07 | Two concurrent requests with the **same** content, different from the current sheet? | If both **read the same version** before either commits, one commits and the other gets `409` (R-20), with no re-read after the conflict. If the second **reads after** the first committed, its content equals the current sheet and it gets `200 sinCambios` (R-17), as does a retry after a lost response. Tests distinguish both interleavings explicitly (T-08 b and c); two HTTP requests sent together are not assumed to have read the same state. | Mentor (proposed) and owner (approved with this precision), 2026-11-08 |
| C-08 | "Serialize the decision": with a lock? | No lock: `SELECT … FOR UPDATE` needs raw SQL, which CLAUDE.md forbids. Optimistic concurrency with a row-version token (R-20), backed by the unique version of `planillas`. Same compare-and-set idea as the ADR-02 claim. | Mentor, 2026-11-08 |
| C-09 | Can the import reschedule a suspended match? | Its scheduled time, yes; its matchday, state, partial score, sheets and versions, no. The match keeps its identity, phase and matchday ("the pending match of matchday 5"; the matchday groups Fecha a Fecha predictions, P-04), and rescheduling never makes it `Jugado`. This replaces a separate operation: the `409` protects results, not schedules. | Mentor (proposed) and owner (approved), 2026-11-08 |
| C-10 | Re-importing an unchanged fixture after results? | `200`, unchanged (R-26). The owner's caveat was real: today `Reactivar()` sets `Programado` on every non-cancelled match, so the current code would silently erase a `Jugado` state. T-17 (a) fails on today's code. | Owner (raised the ambiguity), 2026-11-08 |
| C-11 | Transitions? | Ordinary and exceptional transitions are distinguished (R-14). Ordinary: the first record, completing or resolving a suspension, and corrections within the same state. Exceptional: changes between result states other than those, and the withdrawal of a sheet; they require a coded rectification reason, kept in the new version. No approval workflow in this milestone. `Suspendido` → `Cancelado` is not available; the Admin can adjudicate. A `Jugado` match later awarded by a regulation decision (for example, an ineligible player) is `Jugado` → `Adjudicado` with `DecisionReglamentaria`. | Owner, 2026-11-08 (rejected v1's "every edge is ordinary") |
| C-12 | Withdrawing a sheet saved on the wrong match? | A new immutable version with `estado: "Programado"`, no content and a rectification reason (R-11 d, R-14); previous versions, goals and cards stay; the Admin's `sub` is recorded; the withdrawn result stops contributing because only the current version counts (§7.1). The match can then be cancelled by import like any `Programado` match. | Mentor (proposed) and owner (approved with reason and audit), 2026-11-08 |
| C-13 | Withdrawal of a team with results? | Blocked (`409`, R-29) until each league's regulation decides; the import never cancels or rewrites a match with a result (R-27). Meanwhile, pending matches of a team that abandons can be adjudicated one by one. | Owner, 2026-11-08 |
| C-14 | Reason codes, and free text? | Codes only. Sporting reasons (R-11): suspension `Clima`, `Luz`, `Disturbios`, `Otro`; adjudication `WalkOver`, `Sancion`, `Otro`. Rectification reasons (R-14) are a separate list. No free text in this milestone: it could carry names (personal data) and would reach A-01's prompt (injection). `Otro` gives no public explanation; formal references to regulation decisions may be added later. | Mentor (proposed) and owner (approved as a minimum list), 2026-11-08 |
| C-15 | Fouls per team and per player? | Out of this Spec: no function of the milestone reads them. Kept in the backlog for disciplinary statistics and AI analysis; leagues keep them in their paper sheets meanwhile. | Mentor (proposed) and owner (approved), 2026-11-08 |
| C-16 | Cards now, even without a fair-play weighting? | Yes: yellow, blue and red, per player, without minutes. GoalFlow stores them and invents no fair-play score; the weighting is P-01 (statistics Spec). A blue card means the player leaves with a substitute allowed and carries no automatic suspension. | Owner, 2026-11-08 |

A-01's policy for corrections stays in ADR-12 (ADR-02 C-09). | Mentor, 2026-11-08 |

### 7.1 Obligations for the statistics Spec (binding)

- Read only current sheets (R-07); never sum across versions. A withdrawn sheet (`Programado`) contributes nothing.
- `Programado`, `Cancelado` and `Suspendido` contribute nothing (P-02).
- `Jugado`: official score = sporting score. `Adjudicado`: official score = `oficial`.
- `Autogol` and `SinAutor` rows never count for a player.
- Administrative goals are not goal rows, so they never reach the scorers table.
- Whether the sporting goals and cards of an `Adjudicado` match count, and what a walkover does to matches played, GF/GC, valla and points, is tournament configuration decided there.
- Fair play must treat `tarjetasInformadas = false` as missing data, never as zero cards.
- Sanctions, deductions and bonuses are kept apart from points won on the pitch.
- Without a baseline, the pilot standings do not reflect matches before the cut-off (decision at Control 1).

- **`xmin` as token** (R-20): Npgsql maps a `uint` row-version property to the system column; the migration must not try to add it (checked in §8). `xmin` is per row version, so a no-op update would still change it; the import already writes nothing for unchanged rows (Spec 005 R-20).
- **Tests that gate interleavings** depend on the store ports being the only path to the database for the save and the import; a direct `DbContext` use in Application would bypass the gate (forbidden by ADR-03 already).

- **Status:** Draft v3 (2026-11-15, S4D2, H17), Phase A.2 after the Phase A review; v2 was approved on 2026-11-14 (S4D1, H16) with one editorial correction in R-04 and one production check in §8.2, and implemented in Phase A (PR #22). v3 brings into the Spec what the code decided and the Spec did not say (R-38, R-07 e, R-23) and adds the missing test of R-35 (T-23; C-29, C-30). History: v1 built from the owner's decisions of 2026-11-14 (retos R1 to R6 with predictions, and decisions D0 to D6); v2 after the owner's review the same day (C-04, C-13, C-14 and C-18 accepted; C-16 accepted as provisional; C-21 accepted with a security condition, so the new endpoints stay disabled in production until Spec 010 is verified; findings A1 to A3: R-23, R-36, R-37, T-20 to T-22, C-25 to C-28). The sporting values of both pilot leagues (P-01, points for a loss, walkover effects, phase format) are **not** confirmed; this Spec defines the structure that holds them and never a default for them.
- **Date:** 2026-11-14
- **Related:** Spec 006 §7.1 (binding obligations, all mapped in §3.3), Spec 005 (amended: R-14, R-19, R-20, R-21, R-25 — the import carries the tournament rules), ADR-06 (rules are data of the tournament, kept as historical configuration), ADR-03 (module `Estadisticas`), ADR-14 (§2.11 keys), Spec 002 §10 and `CLAUDE.md` (public endpoints without a rate limit; C-21), Spec 010 (rate limiting, H18; out of scope here)

> Requirement and test IDs are local to this Spec ("Spec 009 T-03"). Appendix A holds the fixtures and their expected results; they were computed by the mentor with a reference implementation of the rules **as written here**, outside the repository. If an implementation result differs from Appendix A, the implementation stops (Estado §4.2 rule 5): neither the rule nor the expected value is adjusted without a decision in the chat.

## 1. Context

Spec 006 stores immutable sheet versions; the current sheet of a match is the one whose version equals `partidos.version`. Nothing reads them yet for statistics. The milestone needs public standings per phase, a top-scorers table and the valla (goals against per team), derived from the current sheets on every request (`CLAUDE.md`: derive, never accumulate). Each tournament has its own rules (points, tie-breaks, fair-play weights, effects of an administrative result), and the rules of the two pilot leagues are still being confirmed. The pilot tournaments are already running: the matches played before GoalFlow are loaded as real sheets with unattributed goals and `tarjetasInformadas = false` where no reliable data exists (Control 1, option (b), confirmed on 2026-11-14 as D0), so every table must show how much of it rests on complete data.

## 2. Goal

For any tournament of a league, anyone can read the standings of a phase, the top scorers and the valla, computed only from current sheets with the tournament's current rules version. The result is deterministic, isolated per league and shows its data coverage. If a rule the calculation needs is missing, the API answers `409 configuracion_pendiente` and never assumes a value. A provisional rules version is visible as such.

## 3. Requirements (EARS)

### 3.1 Tournament rules: stored model (module `Torneos`)

| ID | Requirement |
| --- | --- |
| R-01 | A table `reglamentos_torneo` shall store immutable versions of a tournament's rules: `id`, `tenant_id`, `torneo_id`, `version` (integer ≥ 1), `estado` (`Provisional` or `Confirmado`, check constraint), `contenido` (`jsonb`, the canonical form of R-03 without `estado`; check `jsonb_typeof(contenido) = 'object'`), `guardado_por` (the Admin's `sub`, `uuid`) and `guardado_en` (database clock). (tenant, tournament, version) is unique. The foreign key to `torneos` is composite with `tenant_id` (ADR-14 §2.11) and `ON DELETE RESTRICT`. The primary key is generated by the server (`Guid.CreateVersion7()`). |
| R-02 | `reglamentos_torneo` shall carry `TenantId`, the EF Core filter `Tenant` and RLS with the tenant policy in the same migration. `goalflow_app` shall have `SELECT` and `INSERT` on it, and **no** `UPDATE` or `DELETE`. |
| R-03 | The **current rules** of a tournament are its `reglamentos_torneo` row with the highest version; a tournament without rows has no rules. The rules have one required member, `estado`, and four optional sections: `puntos` {`victoria`, `empate`, `derrota`}; `desempate` {`criterios` (list), `directoRecursivo` (boolean)}; `fairPlay` {`amarilla`, `azul`, `roja`}; and `adjudicacion`, an object whose keys are a subset of {`WalkOver`, `Sancion`, `Otro`} (the adjudication reasons of Spec 006 R-11 c). Each key holds {`puntosGanador`, `puntosPerdedor`, `puntosEmpate`, `deduccionPerdedor`, `deduccionEmpate`, `cuentaComoJugado`, `golesOficialesEnTabla`, `golesOficialesEnValla`, `golesDeportivosEnGoleadores`, `tarjetasEnFairPlay`}. Every member of a present section is required. |
| R-04 | The criteria of `desempate.criterios` come from the closed list `PuntosDirectos`, `DiferenciaDeGolesDirecta`, `GolesAFavorDirectos` (the **direct** criteria) and `DiferenciaDeGoles`, `GolesAFavor`, `FairPlay` (the **general** criteria). General points are never in the list: they are always the implicit first criterion (R-17). An empty list is valid: every tie stays unresolved (R-20). |
| R-36 | The state `Confirmado` shall be a **declaration** by the league's Admin and nothing more: the backend does not verify it against any official table, and no calculation depends on it. Two rules versions that differ only in `estado` shall give identical tables, except for the `reglamento` member of the response. |

### 3.2 Import contract (amends Spec 005)

| ID | Requirement |
| --- | --- |
| R-05 | The body of `PUT /{slug}/admin/torneos/{codigo}` (Spec 005 R-14) shall accept an optional member `reglamento` with the shape of R-03. Spec 005 R-15 applies inside it: an unknown member, including any identifier or `version`, is `400`. |
| R-06 | The import shall validate `reglamento` together with the fixture and return **every** error with its path and code (Spec 005 R-17, `422`, nothing written). Rules: **(a)** `estado` is `Provisional` or `Confirmado`; **(b)** points and deductions are integers 0 to 10; **(c)** `victoria` > `empate` ≥ `derrota`; **(d)** in each adjudication reason, `puntosGanador` ≥ `puntosEmpate` ≥ `puntosPerdedor`; **(e)** a criterion is one of R-04 and appears at most once; **(f)** the direct criteria present form one contiguous block of the list; **(g)** `FairPlay` in the list requires the `fairPlay` section; **(h)** fair-play weights are integers 0 to 100; **(i)** a present section has all its members, including `directoRecursivo` (an absent member is an error, never a default). The keys of `adjudicacion` are members of the contract: an unknown reason is an unknown member, so `400` (R-05). The validator is a pure domain service in `GoalFlow.Domain.Torneos`. |
| R-07 | When the import is valid, the system shall, in the import's transaction: **(a)** with `reglamento` absent and no stored rules, write nothing for rules; **(b)** with `reglamento` present and no stored rules, insert version 1; **(c)** with `reglamento` equal to the current rules (canonical comparison of `estado` and content: criteria order matters, the order of `adjudicacion` keys and of members does not), write nothing (Spec 005 R-20); **(d)** with a different `reglamento`, insert version *n* + 1; **(e)** with `reglamento` absent and rules stored, answer `409` with the body of Spec 005 R-21, `{"conflictos": [{"tipo": "reglamento", "clave": "<tournament code>"}]}`, and write nothing: omitting is never deleting (Spec 005 R-21). Inserted versions store the authenticated Admin's `sub` in `guardado_por`. |
| R-08 | The import response (Spec 005 R-19) shall add a collection `reglamento` with `creados`, `actualizados` and `sinCambios`: R-07 (b) counts one created, (d) one updated, (c) one unchanged, (a) all zero. |
| R-09 | If two imports insert the same rules version concurrently, then the loser shall get `409` (Spec 005 R-23), never `500`, and persist nothing. |
| R-10 | `guardado_por` shall never appear in any response body or log. The import log (Spec 005 R-25) may add the rules version and state. |
| R-38 | The errors of R-06 shall use these paths and codes (adopted from the Phase A implementation, C-29). Paths start with `reglamento.` and name the member in the request's spelling; an adjudication reason keeps its key (`reglamento.adjudicacion.WalkOver`). **(a)** `reglamento.estado`: `estado_invalido`. **(b)** and **(h)** the member: `valor_fuera_de_rango`. **(c)** `reglamento.puntos`: `puntos_no_decrecientes`. **(d)** `reglamento.adjudicacion.<M>`: `adjudicacion_no_decreciente`. **(e)** `reglamento.desempate.criterios[<i>]`: `criterio_invalido` (not in the closed list, exact spelling) or `criterio_repetido`. **(f)** `reglamento.desempate.criterios`: `criterios_directos_no_contiguos`. **(g)** `reglamento.fairPlay`: `fair_play_requerido`. **(i)** the absent member: `miembro_requerido`. A rule that compares members ((c), (d)) is evaluated only when every member it compares is present and in range, so one wrong value gives one error. |

### 3.3 What a match contributes (implements Spec 006 §7.1)

| ID | Requirement |
| --- | --- |
| R-11 | Statistics shall read only the **current sheet** of each match (Spec 006 R-07) and never combine rows of two versions. All the data of one response shall come from one database snapshot: a transaction at isolation `REPEATABLE READ` that writes nothing, with the tenant set as in every transaction (Spec 002). |
| R-12 | A match whose state is `Programado` (including a withdrawn sheet), `Cancelado` (including the exception of Spec 006 C-32) or `Suspendido` shall contribute nothing: no match played, points, goals, valla, scorers, cards or coverage denominator. |
| R-13 | A `Jugado` match shall contribute with its sporting score: one match played for each team, a win, draw or loss with the points of `puntos`, GF and GC for the table, GC for the valla, its `Jugador` goal rows to the scorers, and its cards to fair play when `tarjetasInformadas` is true (when it is false, the match counts as **missing** card data, never as zero cards). |
| R-14 | An `Adjudicado` match with reason *M* shall contribute according to `adjudicacion.M` and its official score: **(a)** points: the winner of the official score gets `puntosGanador` and the loser `puntosPerdedor`; with an equal official score each team gets `puntosEmpate`; **(b)** deductions: the loser gets `deduccionPerdedor` and, with an equal official score, each team gets `deduccionEmpate`; they are kept apart from points (R-16); **(c)** match played, win, draw and loss only if `cuentaComoJugado`; **(d)** the official score counts in GF and GC (and so in the direct criteria) only if `golesOficialesEnTabla`; **(e)** the official goals against count in the valla only if `golesOficialesEnValla`; **(f)** its `Jugador` goal rows count for the scorers only if it has a sporting score and `golesDeportivosEnGoleadores`; **(g)** its cards count for fair play (under the rule of R-13) only if it has a sporting score and `tarjetasEnFairPlay`. Administrative goals are not goal rows, so they never reach the scorers. |
| R-15 | `Autogol` and `SinAutor` rows shall never count for a player. |

### 3.4 Standings of a phase

| ID | Requirement |
| --- | --- |
| R-16 | The standings of a phase shall have one row per **team of the phase**: a participation `Inscrito` that is the home or away team of at least one match of the phase that is not `Cancelado`. Each row holds: `posicion`, `equipo` {`codigo`, `nombre`}, `pj`, `pg`, `pe`, `pp`, `gf`, `gc`, `dg`, `puntosPorResultado`, `deducciones`, `puntos` (= `puntosPorResultado` − `deducciones`, may be negative), `partidosConTarjetasComputables` and `partidosConTarjetasSinInformar` (R-21). Only matches of that phase count. |
| R-17 | The order shall be computed by partitions: the implicit first criterion is `puntos`, descending. Each later criterion is applied to a **group** of teams still tied: it computes a value per team and splits the group by value (descending; `FairPlay` ascending). If the group does not split, the next criterion is applied to the same group. A subgroup of one team is resolved. A subgroup of two or more continues as R-18 says. |
| R-18 | **Direct criteria** shall be computed with R-13 and R-14 restricted to the matches of the phase, all legs, whose two teams belong to the **block group**: the group that entered the block of direct criteria. `PuntosDirectos` uses points by result and ignores deductions. **Where `directoRecursivo` is true**, when a direct criterion splits a group, each subgroup of two or more teams that is **strictly smaller** than the group restarts at the first direct criterion of the list, as its own block group. Otherwise, including when `directoRecursivo` is false, the subgroup continues with the next criterion, keeping the same block group while the next criterion is direct. A general criterion that splits a group sends each subgroup to the next criterion of the list, never back to an earlier one. |
| R-19 | **General criteria:** `DiferenciaDeGoles` and `GolesAFavor` use the row values of R-16. `FairPlay` is Σ (weight of the color × quantity) of the counted cards (R-13, R-14 g) of the team's players in the phase, the lower the better. If any team of the group has at least one counted match with `tarjetasInformadas = false`, then `FairPlay` shall be **omitted** for that group: the omission is recorded with the teams that lack data and their number of matches, and evaluation continues with the next criterion and the same group. |
| R-20 | When the criteria are exhausted, the teams still tied shall share a position: standard competition ranking (1, 2, 2, 4). Their rows are ordered by team code with an **ordinal** comparison, which carries no sporting meaning. The response shall list each unresolved tie in `empates`: `posicion`, `equipos` (codes), `motivo: "criterios_agotados"` and `criteriosOmitidos` [{`criterio`, `motivo: "tarjetas_no_informadas"`, `equipos` [{`codigo`, `partidosSinInformar`}]}]. A tie resolved by a later criterion is not listed. |
| R-21 | The standings shall include fair-play coverage: per row, the counted card matches of the team and how many have `tarjetasInformadas = false` (R-16); and for the phase, `cobertura` {`partidosConTarjetasComputables`, `partidosConTarjetasSinInformar`}, counting each match once. These numbers are shown even when `FairPlay` is not a criterion. |

### 3.5 Top scorers and valla (whole tournament, every phase)

| ID | Requirement |
| --- | --- |
| R-22 | The top scorers of a tournament shall list each registered player with at least one counted `Jugador` goal (R-13, R-14 f) in any phase: `posicion`, `jugador` {`codigo`, `nombre`}, `equipo` {`codigo`, `nombre`} (the player's team in this tournament) and `goles`. Order: goals descending; ties share the position (R-20) and are ordered by player code (ordinal). |
| R-23 | The top scorers shall include `cobertura` over the **scorer-counted matches** (those whose `Jugador` rows count by R-13 or R-14 f): `partidosComputables`; `partidosConGolesSinAutor` (with at least one `SinAutor` goal); `golesTotales` (the sum of their sporting scores); `golesDeJugador` (`Jugador` rows: exactly the sum of `goles` over the top-scorers rows); `autogoles` (`Autogol` rows); `golesSinAutor` (`SinAutor` rows); and `golesConAutor` (= `golesDeJugador` + `autogoles`). The invariant `golesTotales` = `golesDeJugador` + `autogoles` + `golesSinAutor` always holds. It also includes `porEquipo` [{`equipo` {`codigo`, `nombre`}, `partidosComputables`, `partidosConGolesSinAutor`, `golesSinAutor`}], where a team's unattributed goals are those credited to it, for every team with at least one scorer-counted match, ordered by team code (ordinal). |
| R-24 | The valla of a tournament shall list each `Inscrito` team with at least one **valla-counted** match (R-13 or R-14 e) in any phase, final phases included: `posicion`, `equipo`, `partidosComputados` and `golesEnContra` (their sum, never an average). Order: goals against ascending; ties share the position and are ordered by team code (ordinal). No winner is declared. |

### 3.6 Missing configuration

| ID | Requirement |
| --- | --- |
| R-25 | The standings of a phase need `puntos`, `desempate` and `adjudicacion.M` for every reason *M* of an `Adjudicado` match of the phase. The top scorers need `adjudicacion.M` for every reason of an `Adjudicado` match of the tournament **with a sporting score**. The valla needs `adjudicacion.M` for every reason of an `Adjudicado` match of the tournament. If something needed is missing (including when the tournament has no rules), then the API shall answer `409` with `{"codigo": "configuracion_pendiente", "faltantes": [...]}`, listing `puntos`, `desempate` and `adjudicacion.<M>` in that order (reasons in ordinal order), and no table. No value is ever assumed. |

### 3.7 Public API

| ID | Requirement |
| --- | --- |
| R-26 | The API shall expose, without authentication: `GET /{slug}/torneos/{codigo}/fases/{orden}/posiciones`, `GET /{slug}/torneos/{codigo}/goleadores` and `GET /{slug}/torneos/{codigo}/valla`. | R-29 | Tables shall be recalculated on every request; no cache. A request shall run a number of database commands that does not depend on the number of matches, teams or players. |
| R-37 | The three endpoints of R-26 shall be mapped only where the setting `Estadisticas:EndpointsPublicosHabilitados` is true. Its default is **false** in every environment, including `appsettings.json` and Production; the test hosts that exercise the endpoints set it to true. While it is false, the three routes answer `404`, exactly like a route that does not exist, and no use case runs. Turning it on in production is the owner's decision, only after Spec 010 is implemented and verified in production (C-21). |

## 4. Non-functional constraints

- **Personal data:** responses carry player codes and names only (Estado §2); no `sub`, no internal identifier (R-10, T-15).
- **Cost:** recomputation per request is bounded by the import limits (Spec 005 R-16: 64 teams, 1,000 matches per tournament) and by a constant number of queries (R-29, T-17). No response time is asserted in CI.
- **Public exposure:** the three endpoints are disabled in production (R-37) until Spec 010 protects them, together with the existing `GET /{slug}/equipos` (C-21).

| C-01 | Baseline for the running tournaments? | Option (b) of Control 1: past matches are real sheets (official scores, unattributed goals where the scorer is unknown, `tarjetasInformadas = false` where cards are unknown). The official tables of each league are the **acceptance oracle** at the cut-off (§8.2), not stored data. | C-02 | Fixed or configurable tie-breaks? | Configurable per tournament from a closed list (R-04), with no default that could be read as official. The real order of each league is P-01, pending. | Owner (R4, D1), 2026-11-14 |
| C-03 | Recursive or not? | A parameter of the rules (`directoRecursivo`). F1 (Appendix A) shows the difference: recursive A, B, C; not recursive A, C, B. The owner's provisional order is the five criteria of F1 followed by `FairPlay`, recursive, pending P-01. | Owner (R1, D1), 2026-11-14 |
| C-04 | What exactly does "not recursive" keep? | The **block group**: the direct criteria after a split keep using the matches of the group that entered the block. In F1, B and C stay tied on the trio's goals for (3 and 3) and go to the general goal difference; computing GF only over B–C would make the rule recursive by accident. This is the reading the owner predicted with in R1. | Mentor (precision while writing v1); owner (accepted in the v1 review), 2026-11-14 |
| C-05 | After a general criterion splits a group, back to the direct criteria? | No: the next criterion of the list (R-18). If the direct block comes later in the list, reaching it is "next", not "back". | Owner (D1.4), 2026-11-14 |
| C-06 | Can the recursion loop forever? | No. It restarts only after a direct criterion **splits** the group, so every restarted subgroup is strictly smaller and the process ends. The loop would come from restarting a group the block did not split, as in a perfect cycle (F2): there the group stays whole and falls through to the general criteria. | Owner (D1.3, with the predicted 3 points, DG 0 and GF 1 per team), 2026-11-14 |
| C-07 | Fair play with missing card data? | Option (a): omitted for the whole tied group, recorded, never computed over the reported matches only, never prorated (R-19). Consequence accepted: in the pilot, fair play cannot break ties that involve matches loaded without cards. | Owner (R2, D2), 2026-11-14 |
| C-08 | Unresolved ties? | Shared position, competition ranking, ordinal code order without sporting meaning, and `empates` saying why (R-20). The server never invents a winner. | Owner (R2, D2), 2026-11-14 |
| C-09 | Where is the walkover score? | In the sheet (`oficial`, Spec 006). The rules hold only its **effects**, per adjudication reason (R-03, R-14). An equal official score uses `puntosEmpate` and `deduccionEmpate`. Points are non-negative; deductions are separate and shown in their own column. | Owner (D3), 2026-11-14 |
| C-10 | Sporting goals and cards of a match adjudicated by sanction? | Configurable (`golesDeportivosEnGoleadores`, `tarjetasEnFairPlay`); the official score decides points and GF/GC (F5). | Owner (R3 case 2, D3), 2026-11-14 |
| C-11 | A red card before a suspension for disturbances? | Contributes nothing: Spec 006 §7.1 stays unchanged. Counting it would need an explicit amendment first. | Owner (R3 case 3), 2026-11-14 |
| C-12 | Rules required in the import? | Optional, by sections; the calculation asks only for what it needs (R-25); states `Provisional` and `Confirmado`; immutable versions with the Admin's `sub`; tables use the current version and say which. A league's rules become `Confirmado` only by an explicit new version from the Admin after the league confirms them, and after the oracle comparison (§8.2). That comparison is an **operational** check by the Admin with documented evidence; the backend does not perform it (R-36, C-26). | Owner (D4; precision A2 in the v1 review), 2026-11-14 |
| C-13 | Is an absent `desempate` the same as an empty list? | No. Absent means "not decided" and the standings answer `configuracion_pendiente`; `{"criterios": []}` means "decided: no tie-breaks", and ties stay unresolved. Same principle as `tarjetasInformadas` and Spec 008 V6: "none" is not "unknown". | Mentor (proposal); owner (accepted in the v1 review), 2026-11-14 |
| C-14 | An import without `reglamento` after rules exist? | `409`, conflict `reglamento` (R-07 e): omitting is not deleting, as for every other item of the import (Spec 005 R-21). Rules change only by sending a new version. | Mentor (proposal); owner (accepted in the v1 review), 2026-11-14 |
| C-15 | Coverage definitions? | Denominators are the matches whose goals or cards count (R-21, R-23), so an adjudicated match enters only by configuration. Coverage per tournament and per team; plus goals with and without an author. The union of both incompleteness indicators is dropped. | Owner (R5, D5), 2026-11-14 |
| C-16 | Deductions in the order and in head-to-head? | General order by `puntos` (result minus deductions); `PuntosDirectos` by points by result in the matches between the teams of the group, without deductions. This is an **interpretation of the regulation**, not a mathematical necessity: the two values belong to different comparison criteria, so applying the deduction in both would not be a double count. ## 7. Out of scope

- Rate limiting of public endpoints: Spec 010 (H18), before the frontend is public (C-21, C-22).
- Groups, knockout phases, qualification and carrying points between phases (ADR-06): only `TodosContraTodos` exists.
- Manual sanctions and deductions not derived from an adjudication (a disciplinary committee's decision). If a league's official table has one, the oracle comparison will show it (§8.2) and a later Spec adds it.
- Accumulated baselines (C-01).
- Any automatic comparison with the leagues' official tables: it is an operational check of the Admin (C-26).
- A public fair-play table, per-player cards and suspensions, goalkeeper valla.
- Publishing the history of rules versions; only the current version is used and returned.
- Cache, events or notifications when a table changes (Pollas reads its own data later).
- The frontend views (H19).

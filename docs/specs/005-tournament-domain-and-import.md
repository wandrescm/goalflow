> Requirement and test IDs are local to this Spec ("Spec 005 T-07").

## 1. Context

Today the `Torneos` module holds only a minimal `Equipo` used to prove isolation. Spec 006 (score sheet, H11) needs tournaments, phases, participations, player registrations and scheduled matches, and the pilot leagues need a way to load them before there is a frontend. ADR-06 decides the model: identity per league, participation per tournament, structure as data, natural keys from league-assigned codes. ADR-14 §2.11 adds composite foreign keys, tenant-scoped uniqueness and server-generated primary keys, because referential and uniqueness checks bypass RLS.

This Spec also closes debt carried since Spec 002 and Spec 003: the architecture rule that forbids `IgnoreQueryFilters` and raw SQL outside the ADR-14 allowlist, and anti-empty guards for the rules that already run on production code.

## 2. Goal

An Admin can load a complete tournament of their league with one idempotent request; re-sending it changes nothing, a cross-league reference is impossible even through raw SQL as `goalflow_app`, and an architecture rule that sees method bodies (including async and lambda code) rejects any `IgnoreQueryFilters` or raw SQL outside the allowlist.

## 3. Requirements (EARS)

### 3.1 Model and schema

| ID | Requirement |
| --- | --- |
| R-01 | The `Torneos` module shall own `Torneo`, `Fase`, `Equipo`, `Jugador`, `EquipoTorneo`, `InscripcionJugador` and `Partido`, in `GoalFlow.Domain.Torneos`. No other module shall reference them except through `Torneos.Contracts`. |
| R-02 | Each of these entities shall carry `TenantId`, have the EF Core filter `Tenant`, and its table shall have RLS with the tenant policy of ADR-14 §2.2, created in the same migration. |
| R-03 | `Equipo` and `Jugador` shall have a code and a name; `Torneo` shall have a code and a name. Codes shall be unique per tenant. `Equipo` gains its code in this Spec. |
| R-04 | `Fase` shall have an order (≥ 1, unique per tournament), a type and a number of legs (1 or 2). The only type in this Spec is `TodosContraTodos`; the type is stored as text with a check constraint. |
| R-05 | `EquipoTorneo` shall be unique per (tenant, tournament, team) and have a state, `Inscrito` or `Retirado` (check constraint). `InscripcionJugador` shall carry its tournament and be unique per (tenant, tournament, player). |
| R-06 | `Partido` shall carry its tournament, phase, matchday (≥ 1), home and away participations (`EquipoTorneo`), an optional scheduled time and a state. The states in this Spec are `Programado` and `Cancelado` (check constraint). Home and away shall differ (check constraint). It shall be unique per (tenant, phase, home, away). |
| R-07 | Every foreign key between these tables shall be composite and include `tenant_id` (ADR-14 §2.11 rule 1). Foreign keys inside a tournament shall also include `torneo_id`: match → phase, match → home and away participation, registration → participation. Registration → player and participation → team, tournament shall include `tenant_id`. Every referenced key shall be a unique key starting with `tenant_id`. All foreign keys use `ON DELETE RESTRICT`. |
| R-08 | Every unique constraint or index on a tenant-scoped table shall include `tenant_id` (ADR-14 §2.11 rule 2). |
| R-09 | Primary keys of the new rows shall be generated by the server with `Guid.CreateVersion7()`; no request shall supply them (ADR-14 §2.11 rule 3). |
| R-10 | The migration shall grant `goalflow_app` `SELECT`, `INSERT` and `UPDATE` on the six new tables and revoke `DELETE` on them and on `equipos`. |
| R-11 | Scheduled times shall be stored as `timestamptz` in UTC. |

### 3.2 Domain rules

| ID | Requirement |
| --- | --- |
| R-12 | The domain shall reject, with a specific exception: an empty or invalid code, an empty name, a matchday < 1, legs other than 1 or 2, an order < 1, and a match whose home and away are the same participation. Codes match `^[A-Za-z0-9_-]{1,32}$`; names are trimmed, 1 to 80 characters, without control characters. |
| R-13 | A pure domain service (no I/O) shall validate a fixture as a whole and return **all** errors, not only the first: (a) team codes unique in the payload; (b) player codes unique in the whole payload, so that a player belongs to one team per tournament; (c) phase orders unique; (d) every match references an existing phase order and existing team codes of the payload; (e) in a phase with 1 leg, an unordered pair of teams appears at most once; with 2 legs, an ordered pair appears at most once; (f) a team plays at most once per (phase, matchday), counting only matches that are not cancelled; (g) at least one phase and two teams; (h) every match of a withdrawn team is cancelled (R-38). |

### 3.3 Import

| ID | Requirement |
| --- | --- |
| R-14 | The API shall expose `PUT /{slug}/admin/torneos/{codigo}` behind the Admin filter of ADR-01 (404 → 401 → 403). The body is the **complete** desired state of that tournament: name, phases, teams with their players, and matches (phase order, matchday, home and away team codes, optional scheduled time with an explicit UTC offset). A team may carry `retirado` and a match `cancelado` (booleans); a missing mark means `false`. |
| R-15 | If the body is not valid JSON, contains a member the contract does not define (including any identifier field), or its route code is invalid, then the API shall answer `400` and write nothing. |
| R-16 | If the body exceeds 1 MiB, then the API shall answer `413`. If it has more than 8 phases, 64 teams, 60 players per team or 1,000 matches, then `422`. |
| R-17 | If the fixture fails R-12 or R-13, or a scheduled time has no offset, then the API shall answer `422` with every error, each identified by its path in the request and an error code, and write nothing. |
| R-18 | When the import is valid, the system shall, in **one** unit-of-work transaction: create what does not exist, update the mutable attributes that differ (tournament, team and player names; phase type and legs; match matchday and scheduled time; participation state `Inscrito` ↔ `Retirado`; match state `Programado` ↔ `Cancelado`) and leave everything else untouched. Rows are recognised only by their natural keys (ADR-06 §2.4). |
| R-19 | When the import succeeds, the API shall answer `200` with, for each collection (tournament, phases, teams, players, participations, registrations, matches), the counts of created, updated and unchanged items. A state change counts as an update of its item. |
| R-20 | When an identical import is sent again, every item shall be reported unchanged and **no row** shall be written (no `UPDATE` of equal values). |
| R-21 | If a phase, participation, registration or match already stored for this tournament is missing from the payload, then the API shall answer `409` listing the missing natural keys, and write nothing. Omitting is never deleting: a team leaves the tournament only through an explicit withdrawal (R-38). League-level teams and players that the payload does not mention are not conflicts. |
| R-22 | If the payload registers a player with a different team than the one stored for this tournament, then the API shall answer `409` and write nothing. |
| R-23 | If a unique constraint of the import is violated by a concurrent request, then the API shall answer `409` and write nothing; retrying the same import shall then succeed. |
| R-24 | Error bodies shall never contain constraint or index names, SQLSTATE codes, database messages, internal identifiers (primary keys) or any data of another tenant (ADR-14 §2.11 rule 4). They may contain natural keys (codes, phase orders, matchdays) of the caller's own tenant, because the Admin of that league is already authorized to read them; R-21 relies on this. |
| R-25 | The import use case in Application shall log through `ILogger<T>`: tenant, tournament code and counts, never a player or team name. |
| R-26 | The import shall not change league catalog rows of other tournaments except the names it updates (R-18), and shall never read or write another tenant's rows. |

### 3.4 Isolation through keys

| ID | Requirement |
| --- | --- |
| R-27 | If, as `goalflow_app` in a transaction for league A, a row references a row of league B through any foreign key of R-07, then the database shall reject it with `23503`, the same SQLSTATE as for an identifier that does not exist. |
| R-28 | When two leagues import tournaments with the same codes, both imports shall succeed and each league shall see only its own rows. |

### 3.5 Query-safety architecture rules

| ID | Requirement |
| --- | --- |
| R-29 | An architecture rule shall analyse the IL of **every method body** of **every type** in the four production assemblies: no namespace filter, nested and compiler-generated types included (async state machines, closure classes, iterator classes), and all instance and static methods, constructors, accessors and local functions, public or not. It shall inspect every instruction that calls or references a method: `call`, `callvirt`, `newobj`, `ldftn`, `ldvirtftn` (method groups of virtual members) and `ldtoken` with a method operand (how expression trees, such as a subquery inside `Where`, reference methods). A reference found in a nested type is attributed to its outermost declaring type. |
| R-30 | The rule shall report a violation for any call of these families: **F1** `IgnoreQueryFilters` (every overload); **F2** EF Core raw SQL: `FromSql*`, `SqlQuery*`, `ExecuteSql*` (sync and async); **F3** ADO.NET commands: any member of a type assignable to `DbCommand`, `DbBatch` or `DbBatchCommand`, or of the interface `System.Data.IDbCommand`; `CreateCommand` or `CreateBatch` on `DbConnection` or `DbDataSource` (and their Npgsql subtypes) and `CreateCommand` on the interface `System.Data.IDbConnection`; and the Npgsql copy/import/export APIs; **F4** `MigrationBuilder.Sql`. Matching resolves the declaring type of the called method, so a call through `NpgsqlCommand` is detected as well as one through `DbCommand`. |
| R-31 | The allowlist shall be pairs (type, family), matched by full type name or base type, never by namespace: types deriving from EF Core `Migration` may use F4; `GoalFlow.Infrastructure.Persistencia.InterceptorDeTransacciones` may use F3. Nothing may use F1 or F2. |
| R-32 | **Anti-empty guard:** on production code the rule shall find the allowed F3 call inside the **async state machine** of `InterceptorDeTransacciones` (`ExecuteNonQueryAsync` in `TransactionStartedAsync`) and the F4 calls of the migrations `Inicial` and `EntregasEventos` (PR A); PR B adds the migration of this Spec to that set without removing any member. If a member is missing, the test fails: a scanner that does not read bodies must not pass. |
| R-33 | The production module-graph test (Spec 002 T-02) shall also assert the modules it evaluated in each layer, exactly as they exist today: Domain {`Tenancy`, `Ligas`, `Torneos`}, Application {`Tenancy`, `Ligas`, `Torneos`}, Infrastructure {`Ligas`, `Torneos`} (Infrastructure has no `Tenancy` namespace: the tenant context lives in `Persistencia`). |
| R-34 | The general rules of Spec 004 shall assert their exact selection: the entity filter rule (Spec 004 T-26) evaluates exactly the set of tenant-scoped entities of this Spec plus `EntregaEvento`; the table rule (T-27) evaluates exactly the corresponding set of tables plus `admins_liga`. Adding a table requires updating that set. |
| R-35 | An architecture rule over the real EF Core model shall check ADR-14 §2.11 rules 1 and 2: every foreign key whose declaring and principal entities both have `TenantId` includes `TenantId`; every unique index or alternate key of an entity with `TenantId` includes it. A second rule over the catalog of the **migrated database** shall check the same for every foreign key between two `goalflow` tables that have `tenant_id`, and for every unique index of such a table (C-22). |
| R-36 | Application may depend on logging **abstractions** (`ILogger<T>`, declared in namespace `Microsoft.Extensions.Logging` but shipped in the **assembly** `Microsoft.Extensions.Logging.Abstractions`) and on no logging implementation. The rule (Spec 001 T-03) evaluates referenced **assembly names**, never namespaces. Its predicate shall be a named function that accepts the assembly `Microsoft.Extensions.Logging.Abstractions` and rejects the assemblies `Microsoft.Extensions.Logging`, `Microsoft.Extensions.Logging.Console`, `Microsoft.EntityFrameworkCore` and `Npgsql`. Once the import logs (R-25), the real Application assembly shall reference `Microsoft.Extensions.Logging.Abstractions` and still pass T-03. |
| R-37 | Spec 001 T-02, T-04 and T-05 shall select all types of their assembly without the `ResideInNamespaceStartingWith("GoalFlow")` filter (Spec 004 C-21). |

### 3.6 Withdrawal and cancellation (added after the owner's review)

| ID | Requirement |
| --- | --- |
| R-38 | Where a team of the payload is marked as withdrawn (`"retirado": true`), the system shall set its participation to `Retirado` and keep its registrations. Every match of that team in the payload shall be marked as cancelled (`"cancelado": true`); otherwise the fixture is invalid (R-13 rule (h)) and the API answers `422`. |
| R-39 | Where a match of the payload is marked as cancelled, the system shall set its state to `Cancelado` and keep the row and its natural key. A cancelled match still counts for rule (e) of R-13 (its pair keeps its identity) and does not count for rule (f) (it frees its team's slot in that matchday). A cancelled match never produces goals, points or statistics (binding for Spec 006 and the statistics Spec). |
| R-40 | When a later import removes the withdrawal or cancellation marks, the system shall return the participation to `Inscrito` and the match to `Programado`. In this Spec every match is `Programado` or `Cancelado`; withdrawal after results is decided in Spec 006. |

## 4. Non-functional constraints

- **No new raw SQL in production** outside the migration (policies, grants, revokes). Checked by R-29 to R-32.
- **Isolation tests** against PostgreSQL 17 as `goalflow_app` (ADR-14 §5); invented data only (`liga-a`, `liga-b`, codes such as `EQ-01`, names such as `Jugador Uno`).
- **One transaction per import**; a 64-team, 1,000-match import completes within the default request timeout locally (measured once, recorded in the PR; not a test).
- **No personal data beyond name and code** (milestone rule): no document, birth date, photo or contact in the model or the contract.
- **Packages:** `Mono.Cecil` is referenced explicitly by `GoalFlow.Tests`, at the version NetArchTest already brings. No other package change.

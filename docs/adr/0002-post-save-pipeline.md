# ADR-02: Post-save pipeline (durable outbox with an in-memory wake-up)

- **Status:** Accepted
- **Date:** 2026-11-04 (S2D5, H07; proposed and accepted the same day after the owner's review of C-11 and C-12)
- **Related:** ADR-03 (modular monolith; requires an amendment to §7), ADR-05 (hosting, connection budget, R-11), ADR-14 (multi-tenancy; requires an amendment to §2.3), ADR-12 (LLM cost and A-01 policy, pending), Spec 004 (pending)

## 1. Context

When an Admin saves or corrects a match, other modules must react: today the planned consumer is A-01 (a match summary generated by an LLM), and later prediction-game scoring. The reaction cannot run inside the HTTP request: it may be slow, it may call a paid external service, and it must not make the Admin wait or fail the save.

The match itself does not exist yet in code (domain model in S3D1, match sheet and `PartidoGuardado` in H11–H12). This ADR builds and proves the delivery mechanism now, with a test-only event and consumer, so that H12 only connects the real producer.

Facts that shape the decision:

1. The API runs as a single process on Render. It restarts on every deploy and, on the free plan, it spins down after 15 minutes without inbound traffic. On a deploy, Render sends `SIGTERM` to the old instance about 60 s after traffic moves to the new one, waits 30 s by default (configurable up to 300 s) and then sends `SIGKILL`. For roughly 90 s, two instances run at the same time.
2. Anything held only in memory (a `Channel<T>`, a timer, an in-flight task) is lost on `SIGKILL`, on a spin-down or on a crash. A graceful shutdown hook may not run at all. ADR-05 R-11 already requires that all in-memory state can be rebuilt from the database, and ADR-05 §2.6 delegates the recovery of post-save work to this ADR.
3. `goalflow_app` sees one tenant per transaction (ADR-14). `IgnoreQueryFilters` is forbidden, there is no superuser in the API, and raw SQL is limited to the allowlist of ADR-14 C-10. `SELECT … FOR UPDATE SKIP LOCKED` is raw SQL and is therefore not available.
4. `ligas` has no RLS and holds only public data (ADR-14 §2.3). It is the only place where all tenants can be listed without crossing isolation.
5. `ExecuteUpdateAsync` runs a single `UPDATE` generated from LINQ, applies the global query filters, returns the number of affected rows and does **not** go through `SaveChanges`, so the `SaveChanges` guard of ADR-14 §2.3 does not protect it. Outside an explicit transaction, RLS makes it affect zero rows without raising an error.
6. Under `READ COMMITTED`, when an `UPDATE` waits for a row locked by another transaction, PostgreSQL re-evaluates its `WHERE` clause after that transaction commits. Two conditional updates on the same row therefore cannot both succeed.
7. Npgsql (6.0 and later; the repository uses 10.0.3) translates `DateTime.UtcNow` inside a LINQ expression to `now()`, and `AddSeconds` to an interval addition. `now()` is the start time of the current transaction, not of the statement.
8. The API's Npgsql pool is capped at 10 connections out of the 15 the Supavisor project allows (ADR-05 C-03). Any background worker consumes from those 10.
9. Idempotent processing does not make an external call happen exactly once: a worker can complete a paid call and die before recording it.
10. When `SaveChanges` runs while a transaction is already active on the context, EF Core creates a savepoint first and, if the save fails, rolls back to that savepoint. The transaction is **not** aborted and stays usable. The entities that failed to save keep their state in the change tracker (an added row is still `Added`), so a later `SaveChanges` on the same context would try them again.

## 2. Decision

### 2.1 The database decides what work exists; memory only wakes the worker

- **Transactional outbox.** Publishing an event writes delivery rows through the producer's own `DbContext`, inside the producer's explicit transaction. The match change and its pending work commit or roll back together.
- The `Channel<T>` carries **only a wake-up hint** (the `TenantId`). Losing a hint never loses work.
- Delivery semantics are **at-least-once**. The system does not promise that a consumer's external effect runs exactly once (fact 9).

### 2.2 Placement: shared namespace `Mensajeria`

- `Mensajeria` is a new shared namespace, like `Hosting` and `Persistencia` (ADR-03 §7). It is infrastructure for reliable delivery, not a business capability, so it is not a module.
  - `GoalFlow.Application.Mensajeria`: the ports. A publishing port (used by producers), a consumer contract (implemented by consumers) and a tenant-source port that lists the `TenantId` of every league.
  - `GoalFlow.Infrastructure.Mensajeria`: the delivery table mapping, the publishing adapter, the `Channel`, the processing loop and the claim and completion operations.
  - `GoalFlow.Api`: registers the adapters and the consumers.
- The tenant-source port is implemented in `GoalFlow.Infrastructure.Ligas`, which already reads `ligas`. The code dependency is `Infrastructure.Ligas → Application.Mensajeria`; `Mensajeria` does not depend on `Ligas`, and no module gains a dependency on `Ligas` (ADR-14 §2.8 holds).
- Business modules may use the `Mensajeria` contracts. They still reach each other only through `.Contracts` (ADR-03 §6); `Mensajeria` must not become a route to couple them. Event types live in the emitting module's `.Contracts` sub-namespace.
- **Amendment required (same PR as the code):** ADR-03 §7 adds `Mensajeria` to the shared namespaces, and `TablaDeModulos.NamespacesCompartidos` adds it too.

### 2.3 One delivery row per consumer

- When an event is published, the publishing adapter writes **one delivery row per consumer registered for that event type**, all in the producer's transaction. Each row has its own state, attempts and lease, so one consumer failing never blocks or completes another.
- Each consumer has a **stable identity** (a constant name). Duplicate consumer names fail at startup.
- **Logical key:** `(tenant_id, event_type, aggregate_id, aggregate_version, consumer)` is unique. A random event identifier alone does not prevent duplicates; it is kept only for tracing (all rows of one publication share it).
- **Publishing never saves.** The publishing adapter only adds rows to the producer's `DbContext`; the producer's own `SaveChanges` writes them. A unique-key violation therefore surfaces **inside the producer's `SaveChanges`**, not inside the publishing call.
- `ON CONFLICT DO NOTHING` would be raw SQL, so the violation is translated where it surfaces: `GoalFlowDbContext` overrides `SaveChanges` and `SaveChangesAsync` and turns **exactly that violation** (a `DbUpdateException` whose inner `PostgresException` has SQLSTATE `23505` and the logical-key index as its constraint name, and nothing else) into the duplicate-delivery exception of `Mensajeria`, keeping the original as the inner exception. Every other error passes through unchanged. An interceptor is not used, because the translation must replace the exception, and an override states that plainly.
- **Effect on the transaction (fact 10):** the transaction is rolled back to the savepoint taken before the save, not aborted. The failed rows stay `Added` in the change tracker.
- **Two kinds of caller, one port:**
  - **Normal publication** (a producer saving an aggregate) does not catch the duplicate-delivery exception. The exception leaves the use case, the transaction is disposed without commit and everything rolls back. In normal operation it cannot happen, because each save increments the aggregate version.
  - **Idempotent publication** (a backfill, or any caller whose contract is "make sure this delivery exists") works **one aggregate per DI scope and per transaction**. It may check first whether the delivery exists, but that check alone does not survive concurrency: two runs (for example the old and the new instance during a deploy) can both see "absent" and both insert. So the caller **also** catches the duplicate-delivery exception, discards the transaction **and the scope**, and counts the aggregate as already done. The scope must go too: its `DbContext` still tracks the failed rows as `Added` (fact 10), and Application cannot clear the change tracker. Because each aggregate has its own scope, a conflict never undoes or contaminates the others.
- The logical key deduplicates **the same aggregate version**. A backfill that reads version *n* while the Admin saves version *n + 1* creates two different keys, and both rows are legitimate. Any rule of the form "one effect per aggregate, whatever the version" belongs to the consumer (for A-01, ADR-12), not to the outbox.
- Publishing an event type that has no registered consumer writes no rows and logs at `Information`.
- **Consequence (accepted):** a consumer registered later does not receive events published before it existed. The outbox delivers work for events published from now on; historical work comes from the source of truth (the saved aggregates), never from replaying old events.
- **Obligation for H14 (A-01):** in the milestone, `PartidoGuardado` has no consumer between H12 and H14, so matches saved in that window would never get a summary. A-01 therefore ships with an **explicit backfill**:
  - it enumerates tenants through the tenant-source port and works one tenant scope at a time;
  - it reads the **current** state of each eligible match, not its version history, so a match corrected three times yields at most one delivery;
  - it creates deliveries through the same publishing port, as an **idempotent publication**: one aggregate per transaction, an optional existence check, and the duplicate-delivery exception caught and counted as done;
  - it respects the A-01 budget and generation policy of ADR-12;
  - it has tests for isolation, coverage of matches saved before A-01 existed and deduplication. Deduplication is tested twice: running it twice in sequence creates nothing new, and two **concurrent** runs over the same match end with exactly one row, with neither run failing.

  It is not built in H08, because `Partido` does not exist yet.

### 2.4 The delivery table

- Table `goalflow.entregas_eventos`, created by `postgres` in an EF Core migration, tenant-scoped like any core table (ADR-14): `tenant_id` with a foreign key to `ligas` (`ON DELETE RESTRICT`), the named EF Core filter `Tenant` and an RLS policy, in the same migration.
- `goalflow_app` gets `SELECT`, `INSERT` and `UPDATE` only. There is no `DELETE` and no retention job in the milestone (§2.10).
- Columns (creation time defaults to `now()` in the migration and is never sent by the application): identifier, `tenant_id`, event identifier, event type, aggregate identifier, aggregate version, consumer, state, attempts, next attempt time, lease token, lease expiry, last error, creation time and completion time. Times are stored in UTC.
- **States:** `Pendiente → EnProceso → Completada`, or `Fallida` (terminal). A row is never deleted on failure.
- `last error` stores only the **exception type** and, for the permanent-failure exception, a **reason code** chosen by the consumer from its own constants. It never stores an exception message. Truncating a message does not make it safe: a message from a driver, a library or a consumer can contain names, values or tokens, and the first 500 characters are enough to leak them.

### 2.5 One processing loop

- A single hosted background service runs one loop. The first pass starts as soon as the host starts (that is the startup recovery); after each pass it waits for a hint on the `Channel` **or** a periodic timer, whichever comes first. There is no separate startup sweep.
- **The loop never stops the host.** Since .NET 6, an unhandled exception in a background service stops the whole host by default. Any exception in a pass (the tenant source, a claim, the database being unreachable) is caught, logged at `Warning` (type only) and retried on the next pass. Only cancellation on shutdown ends the loop.
- Each pass enumerates the tenants through the tenant-source port and processes them **one after another**. For each tenant it creates its own DI scope, sets the tenant from the enumerated value (ADR-03 §8, ADR-14 §2.4), claims a bounded batch, processes it and moves on. The loop uses **one database connection at a time** (fact 8).
- The `Channel` is bounded, with `BoundedChannelFullMode.Wait` and a single reader. Neither `DropOldest` nor `DropNewest` is used.
- **The hint is sent by the infrastructure after the commit, not by the producer.** The publishing adapter records the tenant in a scoped list of pending hints. A scoped transaction interceptor in `Infrastructure.Mensajeria` sends them with `TryWrite` in its committed hook, and discards them when the transaction rolls back or is disposed without commit. A hint sent before the commit would wake the worker for a row it cannot see yet; a hint after a rollback would wake it for nothing. `TryWrite` never awaits capacity: a full channel drops the hint, and the next timer pass finds the work in the database.
- On shutdown, the loop stops claiming, cancels in-flight consumers through their `CancellationToken` and **writes nothing** for them: no failure, no release, no attempt change. A cancellation caused by shutdown is not a consumer failure. Interrupted rows become claimable again when their lease expires.

### 2.6 Claim: compare-and-swap with `ExecuteUpdateAsync`

- A claim runs in a **short explicit transaction** opened through the unit-of-work port (ADR-14 §2.3), with no external call inside it. It reads a bounded list of candidate rows and claims each one with an `ExecuteUpdateAsync` whose `WHERE` clause repeats the availability condition:
  - `Pendiente` and next attempt time `<=` now, or
  - `EnProceso` and lease expiry `<` now.

  A worker claims only deliveries whose consumer is **registered in its own host**. During a deploy, the old instance does not know a consumer added by the new version, and it must not claim, fail or retry that consumer's rows. A delivery whose consumer is no longer registered anywhere stays `Pendiente`; that is visible in SQL and accepted.

  The update sets `EnProceso`, a new lease token generated by the worker, the lease expiry (now + lease duration) and attempts + 1. The claim succeeds only if it affected exactly one row (fact 6). Then the transaction commits.
- **Attempts are counted at claim time,** so a delivery that crashes the process still consumes an attempt and cannot loop forever. A row whose attempts have reached the maximum is **never handed to a consumer again**. When a pass finds such a row available (`Pendiente`, or `EnProceso` with an expired lease), it moves it to `Fallida` with the same compare-and-swap, in the claim transaction, without running the consumer.
- **Example with a maximum of 5:** a consumer that crashes the process on every delivery runs 5 times. After the fifth crash, the row stays `EnProceso`, because the process died before it could update it. It turns `Fallida` only on a later pass, after its lease expires. If no worker ever runs again, the row does not change by itself.
- **The database clock decides every timestamp.** Time comparisons, lease expiry, next attempt time and completion time are computed with `DateTime.UtcNow` inside the LINQ expression, which Npgsql translates to `now()` (fact 7), and creation time comes from the column default. The application may send a **duration** as a parameter (the backoff, the lease length), never a **timestamp** from the instance clock. The clocks of the two instances during a deploy are never compared. Because `now()` is the transaction start time, claim and completion transactions must stay short.
- **The adapter requires an active transaction** before any `ExecuteUpdateAsync` on the delivery table and throws a specific exception otherwise. Without this check, a missing transaction would look exactly like losing the race: zero rows, no error (fact 5).
- `ExecuteUpdateAsync` never sets `tenant_id`; RLS rejects any row of another tenant anyway.

### 2.7 Processing and completion: fencing by lease token

- After the claim commits, each claimed delivery is processed in a new DI scope with the tenant set. The consumer receives the tenant, the event identifiers, the aggregate version and the **attempt number**. It re-reads current state through its own unit of work; the event carries no match data (ADR-03 §6).
- No transaction stays open while a consumer works.
- Each consumer has a timeout that must be **shorter than the lease duration**. The host fails at startup if it is not.
- **Completion and failure** are separate short transactions with an `ExecuteUpdateAsync` conditioned on `id`, state `EnProceso` **and the worker's lease token**. A worker that lost its lease affects zero rows and must not assume success. Fencing protects the database state only; it cannot undo an external call already made.
- **Logs** record the delivery id, tenant, event name, consumer, attempt, the exception **type** and the types of its inner exceptions, and the stack trace. They **never** record an exception message, at any level, `Debug` and `Trace` included: a log level is a setting that someone may raise in production to diagnose a problem, so it is not a privacy boundary. The exception object is never passed to `ILogger` as such, because the providers write its message. This costs diagnosis, and it is accepted for the milestone.
- **Outcomes:**
  - The consumer returns normally: `Completada`.
  - It throws any other exception: back to `Pendiente`, with next attempt time = now + exponential backoff.
  - It throws the specific permanent-failure exception from `Mensajeria`: `Fallida` immediately.
  - Its timeout expires: treated as a retryable failure.
- **Uncertain external effects:** a delivery may reach a consumer more than once (attempt number > 1, or an expired lease). A consumer whose effect is not idempotent, such as a paid LLM call, must detect redelivery and decide what to do; the dispatcher never assumes. The policy for A-01 belongs to ADR-12.

### 2.8 Initial values (configuration, not constants)

| Setting | Initial value |
| --- | --- |
| Channel capacity | 64 hints |
| Timer period | 60 s |
| Batch per tenant per pass | 10 deliveries |
| Lease duration | 5 min |
| Consumer timeout | 2 min (must be shorter than the lease) |
| Maximum attempts | 5 |
| Backoff | 30 s × 2^(attempt − 1), capped at 30 min |

Tests use shorter values through configuration.

**These are configuration values, not latency guarantees.** With no backlog and the service running, a delivery whose worker died right after claiming it is reclaimed about one lease plus one timer period later (≈ 6 min with the initial values), plus the duration of the pass. With a backlog, passes take longer, because tenants are processed in sequence and in batches. While the free service is asleep, nothing runs at all, so there is **no upper bound**. The 3-minute margin between the consumer timeout (2 min) and the lease (5 min) covers cancellation and coordination, but it does not replace fencing, and it cannot force an external call to honour cancellation.

### 2.9 Reading `ligas` outside a transaction (ADR-14 amendment)

- **Amendment required (same PR as the code):** ADR-14 §2.3 gains a **second exception** besides slug resolution. The tenant-source adapter reads **only the identifiers** of `ligas`, without a transaction and without context, solely so that the processing loop can open one isolated scope per tenant.
- It grants nothing on any other table and does not involve `IgnoreQueryFilters`, a superuser or a cross-tenant query on tenant-scoped data. ADR-14 C-12 is updated to say "the only two reads".

### 2.10 Out of scope for the milestone

- A retention or cleanup job for completed rows. At the pilot's volume (two leagues, tens of matches per week) the table stays small. It is revisited after the milestone.
- Polly or other in-memory retries. The outbox already provides durable retries; in-memory resilience is evaluated in ADR-12 for the LLM HTTP adapter.
- Any LLM client, A-01, notifications or statistics logic.
- An Admin view of failed deliveries; `Fallida` rows are visible through logs and SQL as `postgres`.

## 3. Rejected alternatives

- **In-memory `Channel` only:** loses every queued job on a deploy, a spin-down or a crash (fact 2). Rejected by ADR-05 R-11.
- **`(PartidoId, Version)` as the source of work:** each consumer keeps the last version it processed, and pending work is every match whose version is higher. It needs no extra table, but it ties recovery to business tables, makes per-consumer attempts, backoff and errors awkward, and scans business data on every pass. The outbox keeps those concerns in one place.
- **`SKIP LOCKED` claim:** best for high contention, but it is raw SQL outside the C-10 allowlist. At GoalFlow's volume, a worker that briefly waits on a row and then gets zero rows is acceptable.
- **Optimistic concurrency with `SaveChanges` and a concurrency token:** works, but it needs a tracked read and a `DbUpdateConcurrencyException` path for a single-row conditional update. `ExecuteUpdateAsync` states the condition directly.
- **Lease expiry by the instance clock:** two instances during a deploy could disagree about expiry.
- **Separate event and delivery tables** (deliveries created lazily by the dispatcher): would let late-registered consumers see past events, at the cost of a second table and a fan-out step in the loop. Not needed for the milestone (§2.3 consequence).
- **`Mensajeria` inside `Persistencia`:** mixes the transaction boundary with delivery, claim and retry concerns.
- **`Mensajeria` as a business module:** it is not a capability and would add rows to the module graph for no isolation gain.

## 4. Consequences

- **(+)** Committed work survives restarts, spin-downs and crashes. A full channel never blocks or fails the Admin's save.
- **(+)** Isolation holds in the background exactly as in requests: one scope and one transaction per tenant, RLS in force, no new raw SQL.
- **(+)** H12 only adds the producer and its atomicity test; the delivery mechanics are already proven.
- **(−)** No upper bound on processing delay (§2.8). While the free Render service is asleep nothing runs, and work resumes when traffic wakes it. A paid plan removes the spin-down, but not crashes or deploys.
- **(−)** At-least-once only: every consumer must be idempotent or handle redelivery explicitly.
- **(−)** One more tenant-scoped table and migration, and two documented amendments (ADR-03 §7, ADR-14 §2.3).
- **(−)** A consumer registered later does not see earlier events. For A-01 this is covered by the explicit backfill required in H14 (§2.3).
- **(−)** The `ExecuteUpdateAsync` path bypasses the `SaveChanges` guard. It is protected by the active-transaction check and by RLS, and both are tested.

## 5. Verification

Spec 004 turns this into EARS requirements and tests. Tests on persistence, claims and isolation run against PostgreSQL 17 connected as `goalflow_app`, never as an owner or superuser. Concurrency tests use two independent scopes, `DbContext` instances and transactions.

| Area | What a passing test must show |
| --- | --- |
| Atomicity | A producer transaction that rolls back leaves no delivery row. Separately, publishing calls `SaveChanges` zero times and leaves the rows `Added`: a rollback test alone cannot see a `SaveChanges` made inside the same transaction. |
| Hint after commit | No hint before the commit; exactly one after it; none after a rollback or a dispose without commit. |
| Restart | Host 1 persists three deliveries with the loop disabled and is disposed. Host 2 starts on the same database and completes all three. |
| Full channel | With the channel full, `TryWrite` returns false, the save succeeds and the delivery is completed by a timer pass. |
| No hint | A delivery inserted without any hint is completed by the timer. |
| Isolation | A scope for league A neither reads nor claims league B's deliveries; the loop processes both leagues, each in its own scope. |
| Double claim | Two workers claim the same `Pendiente` row concurrently: one affects one row, the other zero. |
| Rolled-back claim | If the winning claim rolls back, the other worker can claim afterwards. |
| Lease | A valid lease blocks another claim; an expired lease allows it. |
| Fencing | A worker whose lease was taken over completes with zero rows affected. |
| No transaction | A claim without an active transaction throws the specific exception; the test distinguishes this from a lost race (zero rows). |
| Database clock | The generated SQL uses `now()` for every time comparison, and a lease actually expires by the database clock. |
| Attempts | A delivery that keeps failing ends as `Fallida` after the maximum attempts; a permanent-failure exception ends it at once; a delivery claimed and abandoned counts an attempt. With a maximum of 5 and a worker that abandons every claim, the consumer runs exactly 5 times; the row stays `EnProceso` until its lease expires; the next pass sets `Fallida` without a sixth run. |
| Safe errors | An exception whose message carries a marker string: the marker appears neither in `last error` nor in any log entry at any level, while the exception type does appear (so the capture is real). |
| One connection | A pass over several tenants, with a consumer that reads the database, never holds more than one open connection. |
| Loop survives | A failing tenant source does not stop the host; the next pass runs. |
| Registered consumers only | A delivery for a consumer that the host does not register is not claimed. |
| Shutdown | Cancelling the host while a consumer runs writes nothing: the row stays `EnProceso` with the same attempts and is reclaimed after the lease expires. |
| Duplicate | Saving a second delivery with the same logical key raises the duplicate-delivery exception from `SaveChanges`; the transaction is still usable afterwards (savepoint), and disposing it without commit persists nothing. Any other database error is not turned into that exception. A test-only idempotent caller, run twice concurrently for the same key, one scope per run, ends with exactly one row and neither run fails. |
| Fan-out | Two test consumers of the same event get two rows; one failing does not stop the other from completing. |
| Startup validation | Duplicate consumer names, or a consumer timeout not shorter than the lease, fail at startup. |
| Event contracts | Architecture test: every event type carries only identifiers (`TenantId`, `Guid`, an integer version). Canary: a fixture event with a data property makes the rule fail. |
| Tenant-scoped tables (C-13) | Every entity in the real EF Core model with a `TenantId` has the `Tenant` filter, and every `goalflow` table with a `tenant_id` column has RLS and a policy (with the documented exceptions). Canaries make each rule fail. |
| Shared namespace | `Mensajeria` is in `TablaDeModulos.NamespacesCompartidos`, and the module-graph rule still passes. |
| Cache rule | Architecture test: every application `IMemoryCache` registered by GoalFlow has an explicit `SizeLimit`; EF Core's internal cache is out of scope. Canary: a container with an unbounded application cache fails, and one with a `SizeLimit` passes. The rule covers DI registrations only; caches built by hand are not detected. |

Deferred to H12 and ADR-12/H14: the real producer's atomicity test, "never publish a result derived from an older version", A-01's uncertain-call and budget tests, and the A-01 backfill tests (§2.3).

## 6. Clarifications

- **C-01** *Build the pipeline before the producer exists (option a) or with H12 (option b)?* Option (a): build and prove it now with a test-only event and consumer; no fake football entities and no public endpoint. Decided by the owner on 2026-11-04.
- **C-02** *Persisted `EventId` (outbox) or `(PartidoId, Version)`?* Outbox with a unique logical key (§2.3). Decided by the owner on 2026-11-04.
- **C-03** *How does a startup sweep find work across tenants under RLS?* It enumerates tenant identifiers from `ligas` and processes each tenant in its own scope and transaction; this needs the ADR-14 amendment of §2.9. Raised by the mentor; resolved by the owner on 2026-11-04.
- **C-04** *What happens when the channel is full?* The channel is configured with `Wait`, but producers use `TryWrite` after the commit and never wait; the timer recovers a dropped hint. The owner pointed out that without a periodic pass a dropped hint would wait until the next restart. Decided by the owner on 2026-11-04.
- **C-05** *Where does the outbox live?* In the shared namespace `Mensajeria`; the tenant-source port is implemented in `Infrastructure.Ligas` (dependency inversion). Decided by the owner on 2026-11-04.
- **C-06** *How is a claim atomic without raw SQL?* A compare-and-swap with `ExecuteUpdateAsync`, with the database clock deciding lease expiry, plus fencing by lease token on completion. Both proposed by the owner on 2026-11-04. The mentor added the active-transaction check (§2.6), because without it a missing transaction is indistinguishable from a lost race.
- **C-07** *One loop or separate startup and periodic sweeps?* One loop; startup is its first pass. Proposed by the mentor and accepted by the owner on 2026-11-04.
- **C-08** *Polly in H08?* No. Durable retries live in the outbox; in-memory resilience is evaluated in ADR-12. Proposed by the mentor and accepted by the owner on 2026-11-04.
- **C-09** *Does a corrected match trigger a new A-01 summary?* Not decided here. The owner's hypothesis (one generation per match, a summary shown only if its source version equals the match version, no automatic retry after an uncertain call) goes to ADR-12. It must be weighed there against late corrections of goal scorers, a common case in amateur leagues. Raised by the mentor; agreed by the owner on 2026-11-04.
- **C-10** *Cache with `SizeLimit` in this block?* Only an architecture rule with a canary, with no cache in production code (§5). Decided by the owner on 2026-11-04.
- **C-11** *One delivery row per consumer created at publish time, or separate event and delivery tables?* One row per consumer at publish time (§2.3). Proposed by the mentor on 2026-11-04. Accepted by the owner the same day, on one mandatory condition: A-01 ships in H14 with an explicit backfill from current match state, with tenant isolation, deduplication and tests. The owner's reasons: two tables would not solve A-01's gap by themselves, and replaying version history would generate unneeded summaries.
- **C-12** *Initial values of §2.8?* Proposed by the mentor and accepted by the owner on 2026-11-04. They are configuration and can be changed without amending this ADR. The owner added that they are not latency guarantees (§2.8).
- **C-14** *What happens to a row after the last allowed crash?* It stays `EnProceso` until its lease expires; a later pass sets `Fallida` without running the consumer (§2.6). Raised by the owner in the attempts prediction on 2026-11-04.
- **C-15** *Does a shutdown cancellation count as a consumer failure?* No: nothing is written, and the lease expires (§2.5). Raised by the mentor on 2026-11-04.
- **C-13** *Does an existing test check that every tenant-scoped entity has the filter and the policy, wherever the entity lives?* No; checked on 2026-11-04. Spec 002 proved isolation table by table, with `Equipo` as the only tenant-scoped table, and the `SaveChanges` guard applies to any entity that has the `Tenant` filter, whatever its namespace. The delivery table is the second tenant-scoped table, and S3D1 will add several more. Spec 004 therefore adds a general rule over the real EF Core model and the database catalog, with canaries. Raised by the mentor.
- **C-16** *The duplicate-key exception aborts the transaction, yet a backfill run twice must neither duplicate nor fail. Is that a contradiction?* It was, until normal and idempotent publication were told apart (§2.3). Normal publication lets the exception surface and the transaction is disposed without commit. Idempotent publication works one aggregate per scope and transaction and catches exactly that exception, because an existence check alone does not survive two concurrent runs. Raised by the owner on 2026-11-04. The premise "aborts the transaction" was itself corrected in C-18.
- **C-17** *If publishing does not save, where is the duplicate-key violation translated?* In the `SaveChanges` override of `GoalFlowDbContext`, the only place where it surfaces (§2.3). Raised by the owner on 2026-11-04 (review of Spec 004).
- **C-18** *Does a unique-key violation abort the transaction?* Not under EF Core: inside an active transaction, `SaveChanges` takes a savepoint and rolls back to it on failure (fact 10). The failed rows stay `Added`, which is why an idempotent caller discards its scope, not only its transaction. Raised by the owner on 2026-11-04 (review of Spec 004); the earlier text was the mentor's error.
- **C-19** *Is a truncated message safe to store?* No (§2.4). Only the exception type and a consumer-chosen reason code are stored. The first version still allowed messages in `Debug` logs; C-21 removed that. Raised by the owner on 2026-11-04 (review of Spec 004).
- **C-21** *Are `Debug` logs a safe place for exception messages?* No: a log level is a setting that can be raised in production. Messages are never logged at any level (§2.7). Raised by the owner on 2026-11-04 (second review of Spec 004).
- **C-22** *Which clock sets the next attempt time?* The database clock, like every timestamp on the table; the application sends durations only (§2.6). Raised by the owner on 2026-11-04 (second review).
- **C-23** *What happens to a delivery whose consumer the running host does not know?* It is not claimed (§2.6). Without this rule, the old instance in a deploy would fail the rows of a consumer added by the new version, and a test host would claim rows left by other tests. Raised by the mentor on 2026-11-04.
- **C-24** *Can an exception in the loop take the API down?* Not any more: the loop catches everything except cancellation (§2.5). Raised by the mentor on 2026-11-04.
- **C-20** *Who sends the hint, and when?* A scoped transaction interceptor, in its committed hook; none on rollback or dispose (§2.5). The producer has no notification code to forget. Raised by the owner on 2026-11-04 (review of Spec 004: no test pinned the moment of notification); mechanism proposed by the mentor.
